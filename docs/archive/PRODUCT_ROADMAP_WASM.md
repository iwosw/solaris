> Продолжай Solaris по этой WASM-редакции LONG TERM PLAN. Решение принято: серверные плагины переходят на WebAssembly Component Model + Wasmtime, публичный контракт `solaris:plugin@0.7.0` задаётся WIT, guest SDK — Rust. Не возвращайся к выбору языка или к развитию Luau-host.
>
> Прочитай применимые AGENTS.md, текущий docs/MEMORY.md, переданный checkpoint и разделы этого файла для первого незавершённого P-этапа. Новое решение отменяет только несовместимые требования старых документов, прежде всего «сохранить Luau». Не игнорируй остальные инструкции. Проверь реальный HEAD и owned diff; сохрани чужую и незавершённую работу. Старый resume.next с CP-001/R1-B зафиксируй как отложенную предметную задачу, а не как приказ сначала развивать прежний runtime.
>
> Начни с P0: проверяемый baseline и настоящий Rust component, исполняемый в ограниченном тестовом host. Не заканчивай P0 документацией, пустым WIT или cargo check. Докажи bounded decoding, ограничения до instantiation и работу trap/cleanup. Не допускай компонент к игровому host до успешной проверки вредоносных длин, вложенности и итогового объёма host-копий.
>
> Затем последовательно закрывай P1–P8 по критериям. Сохрани `mc-script` как runtime-независимую границу, создай один `mc-plugin-host`, не добавляй второй router/journal/outbox или runtime-provider framework. Существующие игровые операции, plugin IDs/storage keys, durable resident handles, receipts и Solaris Loader перенеси без подмены семантики. Один Store на плагин, callbacks последовательны, guest execution вне simulation owner.
>
> Временно сохранённый Luau допускается только для контролируемого перехода и изолированных сравнений. Один production deployment не запускает оба пути. После проверок P8 удали Luau production runtime, main.lua/rules.lua execution, старые bindings и временные переключатели. Отсутствующий обязательный gate запрещает объявлять cutover завершённым.

Уже реализованные в P-этапах API/lifecycle/budget результаты не пиши заново: проверяй применимость evidence, добавляй только новую игровую вертикаль. Контентные ветки D/E остаются зависимыми; перенос runtime не разрешает переписать весь settlements game design или ядро.
>
> За один checkpoint доводи один конечный исход до предусмотренных проверок. Не подменяй gameplay-прогон подготовкой, mock, старым PASS или уменьшенной нагрузкой. При блокере сохрани owned diff, точные receipts и одно следующее действие. Не делай push, merge, release или изменение production deployment без отдельного разрешения.

## 2. Конечная цель и границы продукта

### 2.1 Основной результат ядра

Обычный vanilla-клиент проходит путь:

```text
вход → перемещение → добыча → крафт → строительство → ферма/бой
     → контейнеры и обмен с другим игроком → выход → сохранение → повторный вход
```

Состояние авторитетно; отказ ничего не меняет; принятые операции не исчезают при перегрузке; предметы не дублируются. Общие механики доступны серверному WASM-компоненту через WIT → проверенные DTO → существующий ScriptBoundary → тот же owner kernel. Для клиентских расширений используется прежний Solaris Loader и тонкие адаптеры; серверный компонент на клиенте не исполняется. [S03] [S04] [S07] [S18]

### 2.2 Порядок приоритетов

1. Обычная игра, многопользовательское поведение и целостность нормальных сохранений.
2. Исполнимый общий API плагинов и реальные клиентские возможности Loader.
3. Измеренная производительность, региональная ownership-модель, ECS и autoscaling.
4. Редкие различия с vanilla и необычные аварийные комбинации.

Внутри нового плана сначала выполняется выбранная миграция P0–P8; приведённый порядок остаётся правилом для продуктовых решений. Раннее исправление повреждения обычного сохранения обязательно, даже если глубокая crash-матрица стоит позднее. Напротив, гипотетическая гонка без воспроизведения не должна вытеснять сломанную доставку груза. [S01] [S03]

### 2.3 Что не входит автоматически

Не начинать Bedrock, исполнение чужих Java server mods, собственный launcher, дополнительный runtime сверх выбранного Wasmtime, микросервисы, Kubernetes-кластер мира, поддержку множества Minecraft-версий или универсальную распределённую транзакционную платформу. Не обещать побитовую worldgen/RNG parity. Не переписывать зрелые доменные crates ради одинакового стиля. [S03] [S04]

Большой settlements overhaul — нагрузка и потребитель общего API. Экономика, культуры, титулы, технологии, цены, конкретные мечи и баланс живут в пакете. Ядро предоставляет общие inventories, entities, navigation, combat, construction, persistence и client contracts.

Сюжетные и контентные defaults в существующей спецификации не следует автоматически объявлять отдельно утверждёнными владельцем. Изменение валютной authority, offline-war правил, масштаба или минимального каталога требует явного продуктового решения. Обычные локальные исправления уже выбранного результата пересогласовывать не нужно. [S11]

### 2.4 Обязательный контракт WASM для всех последующих этапов

Это рабочая сводка [спецификации, §§2–9][S18], а не альтернативная API-схема. Она действует и в поздних CP-этапах: ни оптимизация, ни новый контент не возвращают старый runtime или обход boundary.

| Решение | Обязательное следствие для плана |
|---|---|
| Один серверный runtime — Wasmtime | Нет универсального выбора VM, native plugins и постоянного Luau fallback; P8 удаляет заменённый путь. |
| Component Model и WIT `solaris:plugin@0.7.0` | Реальные component bytes; exact manifest version плюс проверка типов/imports/exports. Core module и совпавшая строка `api` не доказывают совместимость. |
| `mc-script` сохраняется | DTO, capabilities, admission, fences, bounded queues и `ScriptBoundary` не зависят от `mlua`, `luaur` или Wasmtime. |
| Один `crates/mc-plugin-host` | Runtime, package lifecycle, compilation, budgets и преобразования WIT ↔ проверенные DTO. Host зависит от `mc-script`, не от игровых реализаций `mc-net`. |
| `crates/mc-script/wit/` и `sdk/rust/` | Один источник публичной схемы для host bindings и отдельно собираемого SDK. Guest SDK не тянет server runtime, ECS, `mc-net` или Wasmtime. |
| Один Store на плагин | Один выделенный host-worker в первом варианте, последовательные callbacks каждого экземпляра, bounded порция работы на scheduling round. Не Store на chunk/entity/region. |
| Simulation owner не исполняет гостя | Мир меняется только через существующие admission/owner kernels. Imports не захватывают world/session locks и не ждут storage, сеть или загрузку chunk. |
| Staging до полного завершения callback | Валидация всего batch и резервирование admission предшествуют публикации; учитывать обязательные guest `realloc`/`post-return` и cleanup. Trap отменяет неопубликованный batch, но не откатывает guest memory: экземпляр отключается. |
| Принятие batch не равно общей транзакции | Каждая команда повторно проверяется owner. Связанные изменения используют существующую inventory/storage/CAS операцию, а не новый transaction framework. |
| Три независимые области прав | Operator grants плагину, право игрового actor и согласие клиента Loader проверяются раздельно. Provenance и plugin generation задаёт host, не гость. |
| Четыре исхода исполнения | Отказ admission; принято в очередь; owner commit/окончательный отказ; внешняя доставка. `request_id` коррелирует ответ, существующий `operation_id` обеспечивает только уже объявленный durable contract. |
| Один durable путь | Сохраняются WAL/receipts, CAS, inventory fences, `DurabilityUnknown` и `ScriptCommitEventOutbox`. In-memory outbox не объявляется restart-durable; его отказ не отменяет уже совершённый commit. |
| Startup — `configure` | Отдельный краткоживущий Store без runtime-полномочий → типизированный `StartupContribution` → текущие validators/StartupData/world contract. `rules.lua` удаляется только после переноса потребителей. |
| Loader остаётся прежней платформой | WIT server ABI, Loader wire/schema и world/storage versions независимы. Нет WASM runtime на Java-клиенте; server-only по-прежнему не требует Loader. |
| Reload — обязательный P6 | Кандидат всего deployment готовится отдельно; поколения/маршрутизация переключаются на безопасной границе. Неуспех до switch сохраняет старый deployment; после успеха globals/timers начинаются заново, durable storage остаётся. |

**Ограничения ресурсов не откладывать до performance-ветки G.** До instantiation установить fuel, epoch deadline, memory/table/instance/stack limits. Отдельно ограничить host allocations, входные и выходные DTO, nested/aliased данные, snapshots, queues, compilation, candidate reload memory и индуцированную игровую работу. Проверка длины после выделения огромного `Vec`/`String` недостаточна. Выбранные bindings и безопасный ограниченный decoder должны выдержать реальные adversarial components уже на P0. Не писать собственный unsafe ABI и не ослаблять `unsafe_code = "forbid"`. [S18] (§§4.1, 7)

Epoch-counter обновляется независимым таймерным источником. Timeout ожидания синхронного guest call не означает остановку его исполнения; fuel/epochs не останавливают заблокированный host import. Все imports обязаны иметь ограниченную стоимость. Compilation выполняется вне simulation, ограничивается отдельно от guest fuel; первый вариант не использует произвольный precompiled/native cache или `Component::deserialize` для пакета. [S18] (§7)

**Dynamic hooks — только через ограниченный precommit-ticket (P5).** Owner проверяет базовые условия и отпускает управление; host последовательно получает `Keep/Cancel` для build либо `Keep/Cancel/Replace(amount)` для damage. Общий deadline включает очередь и всех handlers; следующий damage-handler видит уже изменённый amount, `Cancel` окончателен. Owner проверяет ticket/revisions/session/permissions перед обычным commit. `Stale` и просрочка не запускают бесконечный retry. Сбой обязательной защиты остаётся fail-closed после отключения Store; без подписчиков дополнительного WASM-ожидания нет. Декларативные protection zones сохраняются. [S18] (§6.2)

**Без автоматической смены форматов.** Замена языка не меняет plugin ID, storage keys, resident identity, world contract или Loader wire. Бинарник/компилятор может измениться при том же нормализованном startup plan без инвалидирования мира. Не выполнять необратимую storage migration внутри init/reload и не переносить произвольную linear memory между поколениями. Численные budgets, версии Wasmtime/wit-bindgen/component toolchain и поддерживаемые targets P0 проверяет и закрепляет; этот документ их не выдумывает. [S18] (§§4.1, 8–9)

## 3. Как читать и исполнять очередь

### 3.1 Обозначения

- **GAP** — незавершённость прямо зафиксирована на опорной ревизии. Перед изменением перепроверить, не закрыли ли её позже.
- **VERIFY** — функция в той или иной форме уже существует; нужен фактический сценарий и исправление обнаруженного расхождения. Не писать вторую реализацию.
- **TARGET** — результат вытекает из продуктового/архитектурного контракта; полнота текущего кода отдельно не установлена.
- **CONDITIONAL** — дальняя ветка или дорогое расширение; выполнять при указанном потребителе и продуктовой необходимости, не «для универсальности».

Указанные зависимости — минимальные. Внутри выбранной ветки по умолчанию придерживаться порядка. Каждому реализуемому пункту всё равно нужны применимые проверки из раздела 5.

### 3.2 Маршруты и новая последовательность

**Сначала миграция runtime:**

```text
P0 — baseline, настоящий component и безопасный исполнимый ABI-прототип
P1 — runtime-независимый mc-script, WIT, mc-plugin-host, Rust SDK
P2 — server-only WASM-плагин в настоящем сервере
P3 — перенос существующих операций и долговечных данных
P4 — configure/StartupContribution и сохранённый Loader
P5 — before-build, затем before-damage через bounded precommit
P6 — strict SIGHUP-reload, generations, shutdown и cleanup
P7 — first-party пакеты, воспроизводимые fixtures, harness/CI
P8 — проверенный cutover и удаление Luau production-пути
```

P0 не зависит от CP-034; P3/P7 переносят **существующие** используемые resident/settlement операции, не требуют предварительно реализовать будущие CP-003–013 или полную кампанию. Поэтому цикл «порт пакета ждёт новый API, новый API ждёт завершения порта» не создаётся. Неисправности исходного gameplay фиксируются отдельно; миграция не делает их поддержанными автоматически. Безопасность нового host и отсутствие обхода permissions/staging обязательны до его игрового допуска. [S18]

**После P8 — сохранённая основная очередь:**

```text
A: CP-001…014 — работник, склад, производство, строительство; пакет уже Rust/WASM
B: CP-015…029 — обычная игра и многопользовательская приёмка
C: CP-030…043 — расширение и проверка общего WIT API/SDK и Loader
F: CP-070…078 — ownership-cutover ядра без смены runtime
G: CP-079…086 — производительность на готовой WASM-платформе
H: CP-088…096 — эксплуатация, сохранения, поставка и приёмка
```

D/E остаются зависимыми контентными маршрутами; CP-087 — отдельный R8 handoff. Базовая runtime-изоляция и сравнительный Luau/WASM baseline выполняются в P0–P8, а не откладываются до CP-076/079. Пункты C, уже закрытые миграцией с применимым evidence, получают `verified-existing`: повторная реализация запрещена.

**Связь с исходными R-этапами settlements:**

```text
R0 / R1          → P3/P4/P7 сохраняют существующие поверхности; A завершает игру
R2 / R3          → D: CP-044…057
R4 / R5          → E: CP-058…063
R6 / R7          → E: CP-064…069
R8              → CP-087 + CP-089…093, с реальными workloads пакета
R9              → CP-094…096, с отдельной полной приёмкой пакета
```

D/E не блокируют scoped server-only ядро и не входят в критерий миграции WASM. Они блокируют заявление о готовности полного settlements overhaul. Общее native-действие можно поднять раньше только вместе с реальным потребителем и тестом.

Нормальное повреждение сохранений, потеря предметов или воспроизводимый обход permissions допускают адресное исправление до следующей стадии миграции. Это не разрешение параллельно наращивать Luau API. Если работа уже шла, безопасно сохранить её diff и курсор перед сменой маршрута.

**Блокеры:** недоступный client gate сохраняет статус `blocked`/`deferred_by_owner` в соответствующем P-этапе. Можно закончить независимую реализацию и её локальные проверки, но нельзя объявлять предшественник принятым, удалять необходимый сравнительный путь или переключать production в обход P8. Отсрочка R0 gameplay acceptance не является автоматической отсрочкой всех WASM/Loader compatibility-проверок; учитывать конкретное разрешение владельца.

Этот документ — каталог исходов. `checkpoint.route` остаётся единственным маршрутом, `docs/MEMORY.md` — единственным живым курсором. В начале миграции явно назначить route `plugins` и owning source для P0–P8; точные архитектурные изменения проверять по owning ADR. После миграции выбирать route конкретного CP, а не всегда `plugins`. Старый cursor, ещё требующий Luau, обновить с явной ссылкой на новое решение, не заводя второй журнал. [S01] [S18]

| Прежний пункт | Новое место / трактовка |

| CP-034, startup-only loader модулей Luau | Удалён как задача. Вместо него проверяется модульный Rust-пакет и самостоятельная сборка через SDK, без гостевого чтения файлов. |
| CP-035, lifecycle с необязательным reload | P6 обязателен; CP-035 проверяет уже добавленные после миграции ресурсы/операции. |

### 3.3 Один checkpoint

Один этап закрывает наблюдаемую возможность вместе с её проверками и документацией. Не закрывать отдельный checkpoint только переносом файла, переименованием, извлечением теста или записью плана.

Если пункт уже реализован **и** есть применимые доказательства, отметить `verified-existing` в курсоре текущего результата и перейти к следующему без искусственного коммита. Если реализован, но необходимого доказательства нет, получить его или честно оставить acceptance pending. Разница между отсутствием функции и отсутствием доказательства должна оставаться видимой.

Слишком большой пункт допускается разделить на завершённые вертикальные результаты с собственными критериями; бесконечные «подготовительные refactor 1/2/3» недопустимы. После checkpoint не запускать автоматически следующую фазу внутри переполненного контекста: сохранить точный resume cursor.

### 3.4 Приёмка, отложенная владельцем

R0 acceptance был отложен. План не отменяет это решение. До явного возобновления разрешены реализация сценариев, подготовка окружения и кодовые проверки, но клиентская приёмка остаётся `deferred_by_owner`. Когда наступит соответствующая стадия и разрешение будет действовать, выполнить настоящий прогон.

Отложенный клиентский gate не запрещает следующую допустимую draft-работу. Он запрещает называть зависимый результат клиентски проверенным, `stabilization`-закрытым или `release-ready` вопреки DoD.

## 4. Рабочий процесс без лишней архитектуры

### 4.1 Первое открытие дерева

Проверить текущие каталоги и нужные инструменты. Не копировать пути чужой машины и не предполагать отсутствие Cargo по старому ответу в чате.

```sh
pwd
git rev-parse --show-toplevel
git rev-parse HEAD
git status --short --branch
rustc --version
cargo --version
cargo fmt --version
python3 --version
python3 -m tools.harness list
```

Для задач, требующих Java/client/oracle, проверить Java/javap, фактическую версию из Gradle, Xvfb, необходимые локальные Mojang artifacts и credentials. Не объявлять отсутствие Java блокером локального изменения Rust/WIT, если его проверки её не используют. Текущая wiring-документация требует Java 25 для соответствующих клиентских профилей. [S06]

Если siblings отсутствуют, core должен по-прежнему собираться. Для интеграционного этапа нужны совместимые sibling-ревизии и пакет целиком: manifest, собранный `plugin.wasm`, config и объявленные assets/bundles. Один Rust source или старый `main.lua` не доказывает работоспособный WASM deployment; production core не запускает guest build.

### 4.2 Границы изменения

Перед кодом записать 5–10 строк: outcome, prerequisite, одна authority, выбранные существующие entrypoints, owned files, acceptance, явные non-goals. Выяснять только вопросы, меняющие реализацию этого результата.

Использовать один путь поиска на вопрос: CodeGraph, когда он доступен и актуален; иначе ограниченный `rg`/прямое чтение. Не читать повторно весь репозиторий, все milestone-архивы и `.ai-bridge` после каждого продолжения.

Предпочитать один существующий planner/commit path. Не создавать worker-specific journal, shadow warehouse ledger, дополнительные fallback modes, generic actor hierarchy или крупные конфиги, когда текущий тип уже выражает нужный случай.

### 4.3 Git и чужая работа

Нельзя `reset --hard`, `clean`, force-push, массово форматировать чужой diff, менять git identity, отключать hooks/signing или коммитить `.analysis`, Mojang jars и credentials. Не трогать `Cargo.lock` без реального изменения зависимостей. В P0/P1/P8 смена Wasmtime/Luau dependencies является такой причиной; сохранить воспроизводимые pins и отдельно учитывать SDK/guest lockfiles. `unsafe_code = "forbid"` не ослаблять.

Этот файл разрешает планирование и описывает реализацию, но сам по себе не даёт разрешения на commit/push/merge/tag. При разрешённом локальном коммите — один обратимый Conventional Commit на завершённый checkpoint в каждом действительно затронутом репозитории. Без такого разрешения сохранить diff и resume snapshot. Разрешение на один репозиторий не распространяется автоматически на siblings. [S01]

### 4.4 Ревью

Самопроверка → один независимый read-only reviewer на итоговый diff, когда среда предоставляет такую возможность и делегирование разрешено. Передать ему только outcome, base, diff, тесты и границы, без всей переписки. Reviewer не пишет код и не запускает новых агентов.

Если независимый агент недоступен, сделать отдельный собственный review-pass и записать `independent_review: not_run`. Не выдавать повторное чтение той же моделью за независимое ревью. Отсутствие reviewer не оправдывает выдуманный PASS. [S01]

## 5. Общая проверка каждого результата

### 5.1 Гейты

| Уровень | Что запускать |
|---|---|
| L0 | Сфокусированный тест затронутого поведения и ограниченная проверка diff/syntax. |
| L1 | Affected-scope tests, `python3 -m tools.harness run fmt`, `python3 -m tools.harness run code-health`; синхронизация CodeGraph, только если на него опирались. |
| L2 | Для code commit/release/milestone close один `python3 -m tools.harness run correctness` на конечном дереве. Он включает formatter, code-health, strict Clippy и workspace/all-target tests. |
| Java/Loader | `python3 -m tools.harness run java`; применимый `loader-live --platform fabric`, `neoforge` или `forge`, когда разрешена настоящая приёмка. |
| Runtime | Реальный server process, persistence/restart и путь production-кода; ни mocks, ни текстовый grep по Rust не подменяют поведение. |
| Клиент | `core-client`, `inventory`, `regression`, `playable`, `replay` или объявленный сценарий внутри существующего harness. Для multiplayer — второй настоящий клиент. |
| Vanilla | Локальные wire-probe/javap/decompiled source/capture ровно целевой версии; неизвестный packet layout нельзя дописать по памяти. |
| Perf | Только профиль/режим, который действительно измеряет выбранную нагрузку; release для perf, debug для обычной разработки. |

При сбое после исправления повторять только упавший gate, если остальные сохраняют ту же `(command, tree fingerprint, environment, scope)` применимость. Не гонять один и тот же зелёный полный workspace без причины. Перед релизом нужен полный набор на его конечной ревизии, а не сумма чужих старых результатов. [S01] [S05] [S06]

Для ограниченной машины исходный курсор предписывает:

```sh
export CARGO_BUILD_JOBS=2
python3 -m tools.harness run correctness
```

Один тяжёлый gate одновременно; без `nice`, искусственных retry и расширения timeout ради зелёного. Не переносить зафиксированную в истории команду с `pkill yes` в автоматизацию: процессные воздействия должны быть ограничены принадлежащими тесту процессами. [S02]

### 5.2 Команды, которые действительно существуют

```sh
# Примеры текущих focused suites, не обязательный список для любого изменения.
cargo test -p mc-net --lib

```

Это каталог примеров, **не shell-скрипт для одновременного запуска всего**. Сначала проверить `list`, prerequisites, актуальные manifests и задачу. Не выдумывать профиль `run settlements`: ECO/BUILD/REC и CP-номера обозначают требования/этапы, а не готовые команды. Новые сценарии и сборка guest fixtures сначала реализуются и объявляются в существующем canonical harness, без второго runner. [S06] [S11] [S18]

### 5.3 Требования к свидетельствам

`--check`, `--prepare`, bare `oracle`, пропущенный тест, не запущенный клиент и Gradle `UP-TO-DATE` не доказывают новое gameplay-поведение. Число выполненных тестов, skipped suites и фактические процессы должны быть видны. Timeout — failure. Ожидание строится на событии/notification/state transition, не на sleeps и периодическом polling. [S01] [S06]

Отчёт checkpoint содержит строки: Cargo baseline; focused runtime; vanilla oracle; client/manual; performance; concurrency; data/protocol; persistence; dependencies; known gaps. Для неприменимого указать `not_applicable` с причиной; для невыполненного — `not_run`, `blocked` или `deferred_by_owner`. `draft`, `stabilization`, `release-ready` — отдельная оценка зрелости по DoD. [S05]

Каждый regression должен иметь правдоподобную ошибку, которую он ловит: потеря stack, повторный эффект, stale generation, нарушение permission, непройденный consumer event. Проверка строки исходника или mock, возвращающий заранее нужный ответ, такого доказательства не даёт.

### 5.4 Сквозные инварианты

1. У фактических items/blocks/entities ровно одна авторитетная запись; projection не становится вторым владельцем.
2. Отклонённая операция не меняет защищаемое состояние. Успешный commit и доставка уведомления клиенту — разные наблюдения.
3. Для transfer сохраняются количества и компоненты предметов. Для craft/consume/break закон баланса учитывает объявленные входы, выходы, расход и остаток, а не наивное равенство числа предметов.
4. Для операций с существующим durable/idempotent контрактом повтор того же operation id не повторяет effect, а иной payload с тем же ID даёт конфликт; новый ID не отменяет revisions/permissions. Это не exactly-once обещание для любых WASM commands, callbacks или сетевой доставки. [S18]
5. Неизвестное/не загруженное состояние не равно пустому инвентарю или отсутствующей деревне.
6. Server-owned работа не получает фиктивную player session; отсутствие владельца онлайн не даёт дополнительных прав.
7. Публикация основана на принятом состоянии. Отказ/отключение одного клиента не отменяет уже зафиксированный исход.
8. Выход за capacity ограничивается до дорогих allocations/effects и явно отражается в status; принятые предметные операции не выбрасываются из очереди молча.
9. Для durable-claim нужен recovery на настоящем storage path; тест сериализации структуры доказывает только сериализацию.
10. Клиентские UI, preview и input выражают намерения, не подтверждают стоимость, урон, владение или права.

### 5.5 Обязательные gates миграции WASM

Полный набор сценариев находится в [приложении A, §11][S18]. Таблица ниже назначает владельца проверки; это названия требований, **не существующие harness profiles**. Обязательный test/fixture не превращается в skip/pass из-за отсутствия артефакта.

| Область | Первый обязательный этап | Что нельзя отложить или подменить |
|---|---|---|
| ABI, component types, imports/exports, toolchain | P0; интеграция P1/P2 | Core module не component; exact `api` не заменяет проверку WIT. |
| Limits до instantiation, loops/stack/memory/table/instance limits | P0/P2 | Fuel не миллисекунды; epoch source независим; синхронный call не остановлен отменой ожидания. |
| Host lifting/decoding, nested/aliased строки и списки | P0, повтор на конечных P3/P4 types | Отказ до неограниченного host allocation; safe API без собственного unsafe ABI. |
| Grants, namespaces, host provenance и поколения | P1/P2/P3 | Включить direct messaging/router paths; permission, admission и Loader consent различны. |
| Staging, malformed batch, trap, post-return/cleanup | P0/P2 | До завершения callback и cleanup нет игровых effects; память guest не считается откатившейся. |
| Storage/CAS/items, replay, DurabilityUnknown | P3/P7 | Проверять прежние реальные данные и effects; не второй journal и не обещание exactly-once всему ABI. |
| Required outbox, closed/lost receiver, late committed result | P3/P6 | Не превращать обязательную доставку в best-effort и не отменять существующий commit ошибкой очереди. |
| Configure/StartupContribution и --check | P4 | Идентичный effective plan сохраняет world contract; --check без world/storage/listener mutations. |
| Precommit tickets / Keep / Cancel / Replace | P5 | Все обещанные sources проходят hook, нет ожидания под lock; обязательная защита остаётся fail-closed. |
| Reload, candidate memory, cleanup/generations | P6 | Весь deployment, late results, init-effects, irreversible data changes, protection; не один plugin swap вместо контракта. |
| First-party/standard pack и старые behavioral assertions | P7 | Настоящие components, реальные IDs/storage keys и проверяемые fixture source; без stub `unsupported`. |
| Vanilla / Loader-required / platform gates | P2/P4/P7 | Подготовка клиента не gameplay PASS; old/new session не смешиваются; клиентский WASM не добавляется. |
| Сравнительные нагрузки и общий resource envelope | P0 baseline → P7 итог | Ноль/несколько/flood гостей, slow storage, event storm, repeated reload; тот же workload, hardware, build, seed, длительность и assertions. |
| Удаление старого production-path и автономная core build | P8 | Проверить dependencies/callers/CI/installer/docs и реальные сценарии, не только grep отсутствующего `lua.rs`. |

`cargo test -p mc-plugin-host` становится доступен **после появления крейта**, не считается командой опорной ревизии. `cargo test -p mc-script`, `cargo test -p mc-test-harness --test plugin_examples`, `cargo test -p mc-test-harness --test plugin_standard_pack` и `python3 -m tools.harness run correctness` берутся из исходной спецификации; перед запуском сверить текущие targets. Точную guest build command и dependency pins записать после успешной проверки P0. Не выдумывать `run wasm` или запуск private backend напрямую.

Изменение WIT, converter, decoder, limits или callback cleanup требует проверки соответствующего нового tree fingerprint; старый safety PASS не распространяется автоматически на новые типы. Post-P8 API-расширения CP-030–043 включают тот же hostile-input/permission/staging контроль, а performance CP-079 не заменяет обязательный допуск P0–P7.

### W. Обязательная миграция серверных плагинов: P0–P8

Порядок и критерии основаны на [спецификации, §§10–14][S18]. Ни один этап не отмечен выполненным этой редакцией. До игры нужно доказать безопасный ABI; до удаления старого runtime — перенести весь реально используемый surface и необходимые пакеты. Существующий item/world/storage contract важнее внешней похожести callbacks.

#### P0. Проверенная база и исполнимый ABI-прототип

**Тип:** TARGET, обязательная миграция. **Зависимости:** фактический preflight, сохранённый owned diff и назначенный маршрут новой задачи.

**Результат:** Настоящий Rust component исполняется в тестовом Wasmtime-host с доказанно ограниченными входом/выходом и lifecycle. Выбраны совместимые стабильные dependency/toolchain версии; есть сопоставимый baseline.

**Работа:** Сверить текущий API по реально вызываемым `ScriptCommand`, `ScriptEvent`, Luau registrations, router и tests. Для каждой используемой возможности назвать caller, capability/grant, DTO, owner commit, result/durability path и пакет. Прочитать strict deployment, startup rules, reload и Loader surfaces, включая прямые branches router. Проверить stable Wasmtime/wit-bindgen/component tooling против MSRV 1.94 и Linux x86_64/AArch64; закрепить реальные версии и команды, не выбирать по `latest` документации. Снять baseline без плагинов и с существующими примерами. Собрать component, проверить imports/exports и минимальные init/event/batch/trap; прототип не становится вторым production host.

**Проверка:** Несовместимый ABI и core module отклоняются. До instantiation действуют fuel/epochs/memory/table/instance/stack limits. На выбранных bindings воспроизводимо проверены oversized/nested/aliased выходы: ограничение срабатывает до неограниченного host-копирования. Проверить trap и guest cleanup/post-return; неопубликованный batch не даёт effects. Зафиксировать host RSS/очереди и baseline latency/ticks, build/seed/hardware/workload. Отдельно результаты проверки поддерживаемых targets, а не предположение по успешной локальной сборке.

**Граница:** P0 не завершается WIT-файлом или cargo check. Не писать unsafe decoder, подключать весь WASI или механически переносить Luau fuel/16 MiB. Пока bounded decoder не доказан, P2 к игровому host не допускается. Численные budgets задаются по измерению, не обещанием WASM-ускорения.

#### P1. Отделение контракта от Luau

**Тип:** TARGET, обязательная миграция. **Зависимости:** P0.

**Результат:** Runtime-независимая граница `mc-script`, один WIT-контракт, отдельно собираемый guest SDK и выделенный `mc-plugin-host` обслуживают рабочую компонентную вертикаль.

**Работа:** Создать один runtime-крейт `crates/mc-plugin-host`; из `lua.rs` извлечь только общие deployment/client/startup metadata и затронутые contract-модули с сохранением полей и проверок. Разместить единственный WIT в `crates/mc-script/wit/`, guest SDK — в `sdk/rust/`. Получать host/guest bindings из него; преобразование во внутренние validated DTO держать в одном месте. Внешний контракт не раскрывает `HostAttached`, `AdmittedScriptCommand`, authorizing plugin ID/generation, engine pointers или ECS. Разделить player identity, session, entity generation, plugin generation и object revision. Переиспользовать прототип и прежние boundary tests.

**Проверка:** Реальный component собирается SDK и проходит через host → существующую boundary. SDK собирается отдельно от сервера; host не зависит от `mc-net`; `mc-script` не зависит от Wasmtime, `mlua` или `luaur`. Старые проверки capabilities/DTO не потеряны. Неверные IDs, ranges, NaN/Infinity, stale/foreign handles и oversized значения отклоняются.

**Граница:** Не переименовывать `mc-script` для красоты, не создавать `wasm_router`, второй schema набор, generic `RuntimeProvider` или crate на каждый интерфейс. Временно сохранённый Luau сравнивается в изолированной миграционной оснастке, не через зависимости runtime-независимого `mc-script`; окончательное удаление — P8.

#### P2. Настоящий WASM-плагин в сервере

**Тип:** TARGET, обязательная миграция. **Зависимости:** P1 и пройденный safety gate P0.

**Результат:** Обычный vanilla-клиент получает приветствие и ответ `/hello` от настоящих внешних server-only компонентов; host подключён из composition root к единственной `ScriptBoundary`.

**Работа:** Реализовать discovery `plugin.toml`/`plugin.wasm`, exact API/types/imports validation, grants, `strict`/`expected`, конфликты IDs/commands и package path/size checks. `--check` проверяет выбранный deployment без world/storage/listener effects. Исполнение: один Engine с переиспользуемыми immutable compiled components, отдельный Store на плагин и один выделенный worker; последовательные callbacks, per-plugin/global queues и bounded fair scheduling. Импорты — bounded logging и подготовленный контекст; mutations, timers и registrations идут staging batch. После полного callback/cleanup проверить весь batch и admission; только потом публиковать.

**Проверка:** Hello/join с настоящим клиентом; неверные manifest/ABI/import/grant останавливают strict startup. Trap одного из двух гостей не ломает второй; partial invalid batch, exhausted fuel, cleanup error и admission overflow не публикуют его effects. `--check` не создаёт мир и не меняет storage. Chat/broadcast/disconnect также не обходят admission. Запуск тестовых пакетов не включает их автоматически в production.

**Граница:** Не считать Store sandbox отдельным процессом. Никакого guest execution под simulation lock, синхронного world/storage I/O в imports, бесконечных очередей или двух runtime в одном production deployment. Полная configure/StartupData вертикаль завершается в P4, не подменяется пустым результатом для пакетов, которым она нужна.

#### P3. Существующие операции и долговечные данные

**Тип:** TARGET, обязательная миграция. **Зависимости:** P2.

**Результат:** Реально используемые старым deployment игровые операции доступны через WIT с прежними permissions, ownership, refusals и durable semantics.

**Работа:** По матрице P0 переносить законченные вертикали: messaging/timers; bounded queries и handles; entity/world mutations/zones/teleport; storage/CAS; inventory и typed results; используемые resident/settlement/order операции. Все команды проходят старые игровые validators/owners; привязка к Store и grants создаётся host. Команда результата поступает следующей доставкой без recursive re-entry. Разделить admission, queued, committed/rejected и delivery; `request_id` не заменяет durable `operation_id`. Сохранить `ScriptCommitEventOutbox`, receipts/fingerprints, CAS, inventory fences и обработку `DurabilityUnknown`.

**Проверка:** Для каждой используемой строки матрицы — реальный WASM caller, capability, owner/result path и прежние behavioral assertions. Старое plugin storage читается новым deployment. Same operation ID/different payload конфликтует; повтор/reconnect/restart не дублирует объявленный durable effect. Проверить inventory revision, conservation компонентов items, foreign namespaces, stale generations, outbox full/closed/lost receiver и committed result после disable.

**Граница:** Не создавать второй журнал/outbox, не отвечать `unsupported` вместо переносимого работающего API. Новые warehouse withdrawal, стройка и полный R1 остаются CP-003–014. Исходный баг не считать исправленным сменой VM; необходимые исправления выделять и доказывать отдельно. Не обещать exactly-once для всех callback/команд или replay обычного memory outbox после restart.

#### P4. Startup и Loader без смены платформы

**Тип:** TARGET, обязательная миграция. **Зависимости:** P3.

**Результат:** `configure(config) → StartupContribution` заменяет startup rules, а существующие client bundles и presentation работают через WASM-команды без новой клиентской платформы.

**Работа:** Исполнять configure в отдельном краткоживущем Store без runtime-возможностей; результат передавать существующим startup validators, `StartupData` и world-contract check. Сохранять смысл нормализованного effective plan независимо от бинарника/компилятора. Подключить реально используемые Loader UI/HUD, audio, payload, views/actions/input/content metadata через те же session/permission/asset/hash paths. Проверка deployment включает configure и init со staging без видимых игровых effects; init не дублируется через дополнительный `server.started`.

**Проверка:** Одинаковый effective plan сохраняет совместимость мира, реально несовместимый отклоняется до изменений. Ошибка configure/init не создаёт мир, storage или listener в `--check`. Server-only клиент проходит без Loader; required fixture проходит реальные предусмотренные platform gates. Consent/permissions/hash/session fences сохранены; disconnect исключает доставку в новую сессию. Отложенный R0 gameplay acceptance фиксируется отдельно от результата Loader compatibility.

**Граница:** Не повышать автоматически Loader wire/schema, API storage или worldgen revisions из-за WIT 0.7.0. Не удалять world-contract и не требовать свежий мир только ради языка. Нет WASM/Java guest runtime на клиенте; скрытое исполнение `rules.lua` после полного cutover запрещено.

#### P5. Ограниченные precommit hooks

**Тип:** TARGET, обязательная миграция. **Зависимости:** P4; существующий общий owner/permission path из P3.

**Результат:** Сначала `before-build`, затем отдельная законченная вертикаль `before-damage` управляют ещё не совершённым действием без исполнения гостя на simulation owner.

**Работа:** Сохранить декларативные zones. При наличии handler owner формирует immutable context и внутренний ограниченный ticket с revisions, затем освобождает управление. Host вызывает handlers в порядке оператора с `plugin_id` как tie-breaker; общий deadline включает очередь и цепочку. Build: Keep/Cancel; damage: Keep/Cancel/Replace(amount), следующий handler видит преобразованный amount, Cancel окончателен. Owner проверяет живой ticket, revisions, session и полномочия, затем исполняет обычный kernel либо типизированно отказывает. Hook не получает mutations, I/O или новые async requests.

**Проверка:** Два handlers, изменение damage, cancel без списания item/нанесения damage; stale/expired/duplicate ticket без повторного effect; queue deadline и отозванные права; программный путь не обходит обещанный hook. Trap обязательной защиты не открывает территорию и не снимает регистрацию после disable Store. Измерить client-visible latency и отсутствие дополнительного ожидания при нуле подписчиков.

**Граница:** Не ждать WASM под world/region lock, не делать бесконечный revalidation retry, не обещать тот же tick/нулевую задержку. Эти hooks не реализуют всю будущую войну/дипломатию CP-058–067. Отдельный администраторский акт снятия защиты нельзя заменить автоматическим cleanup.

#### P6. Reload, shutdown и ресурсная очистка

**Тип:** TARGET, обязательная миграция. **Зависимости:** P5.

**Результат:** Strict SIGHUP-reload безопасно заменяет весь совместимый deployment, сохраняя определённые исходы операций, durable state и обязательную защиту.

**Работа:** Проверить/скомпилировать кандидатов вне активных Store, включая суммарную память старых и новых экземпляров. Сверить identities/order/command ownership/startup contributions/client contract/effective grants: несовместимое изменение требует restart. Выполнить candidate init в staging. На безопасной границе остановить новые callbacks старым экземплярам; admitted work довести до определённого исхода либо отказать до commit. Атомарно переключить routing/generations и разрешить кандидатные effects, затем очистить старые временные ресурсы. Host владеет timers/subscriptions/registrations/UI/pending requests независимо от best-effort shutdown.

**Проверка:** Failure компиляции, validation, instantiation/init и нехватка candidate memory до switch оставляют старый deployment. Successful switch не дублирует init-effects. Late timers/results не попадают в новый Store/session; committed operation остаётся доступна по storage contract. Protection/durable storage/resident identity не удаляются при trap. Infrastructure delivery/storage failure отличим от guest failure; нельзя маскировать его отключением одного пакета.

**Граница:** Globals/timers после успешного reload начинаются заново; durable storage остаётся. Никакого raw-memory migration, обязательной новой save-state/load-state схемы, irreversible storage migration в init или бесконечного auto-restart. Не считать shutdown гарантированным при аварии.

#### P7. First-party пакеты и интеграционные gates

**Тип:** TARGET, обязательная миграция. **Зависимости:** P6.

**Результат:** Реально используемые пакеты, стандартный pack, startup/Loader consumers и прежние интеграционные сценарии работают через воспроизводимые Rust components.

**Работа:** В отдельном `../solaris-default-plugins` с его AGENTS портировать выбранные пакеты и реальные зависимости из P0, сохранив IDs/storage keys/handles без необоснованной миграции. Rust-модули собираются заранее в `plugin.wasm`; гость не получает runtime require или файловый доступ. Добавить воспроизводимую сборку SDK и проверяемых по исходнику fixtures в существующий harness/CI. Связать core, SDK/WIT, packages, fixtures и Loader конкретными revisions/hashes. Production core build не запускает guest compiler и не требует siblings. Сравнить baseline P0 на прежних workloads и двух реальных Rust-плагинах; настроить budgets по evidence.

**Проверка:** `plugin_examples`, `plugin_standard_pack`, необходимые startup/storage/reload/client scenarios — через настоящие components с исходными assertions. Required fixture не пропускается молча. Ноль плагинов, нормальные пакеты, flood/infinite guest, event storm, slow storage и повторный reload: tick p50/p95/p99, plugin latency, queues, CPU/RSS, errors на сопоставимом hardware/build/seed/population/duration. Не смешивать debug/release и не подменять прежний gate облегченным.

**Граница:** Это перенос существующего пакета, не полное завершение R1–R9. Нет sibling — пакетный gate blocked, без копии в ядре. Не создавать transpiler Luau→Rust, второй runner или пакеты-заглушки ради удаления старой VM. Переносить сравнение baseline в поздний CP-079 нельзя.

#### P8. Единственный production-путь и удаление Luau

**Тип:** VERIFY, обязательный cutover. **Зависимости:** P0, P1, P2, P3, P4, P5, P6, P7 с применимыми обязательными проверками.

**Результат:** В коде и поставке один серверный runtime Wasmtime; внешний Rust-плагин собирается в component и подключается без пересборки сервера. Старые используемые сценарии, startup, durable operations, reload и Loader сохранены.

**Работа:** После gates завершить переключение composition root на новый host. Удалить исполнение `main.lua`/`rules.lua`, bindings/prelude, `lua-runtime`, ненужные `mlua`/`luaur`, старые entrypoints, временные runtime switches и адаптеры старых пакетов. Проверить runtime callers, dependency graph, workspace, SDK/fixtures, CI/harness, installer, example configs и документацию. Изменение Cargo.lock здесь имеет конкретную dependency-причину. Обновить AGENTS/ARCHITECTURE/PLUGINS/операторский guide как один актуальный контракт; исторические receipts не переписывать.

**Проверка:** Полный конечный L2 и применимые P0–P7 acceptance gates на согласованных revisions; самостоятельная production-сборка core без siblings и guest compiler; реальный внешний пакет, storage/recovery, server-only и Loader-required, permissions, reload и ресурсные ограничения. Отсутствие Luau dependency/production caller — structural evidence, а не замена поведенческих тестов. Старый package не исполняется скрытым fallback.

**Граница:** Удалять сравнительную Luau-оснастку можно только после сохранения требуемого baseline/evidence. Не закрывать P8 с неперенесённой используемой возможностью или обязательным недоступным gate; сохранять `code_done`/`blocked` отдельно. Изменение исходного startup не даёт разрешения менять работающий production deployment, пушить или публиковать релиз.

**Следующий предметный результат:** CP-001 на Rust/WASM-пакете. Если CP-001 уже закрыт адресным исправлением при переносе и это доказано, отметить `verified-existing` и идти к CP-002, не дублировать patch.

### A. Завершить активную цепочку R1: работник → склад → производство → строительство

После P8. CP-001 продолжает прежний R1-B в портированном Rust/WASM-пакете; CP-003–007 закрывают названные исходным планом предметные пробелы ядра. Уже исправленное при переносе повторно не реализовывать. Остальные пункты доводят существующий R1 до наблюдаемого хозяйственного цикла, не создавая нового settlements engine. Основные источники: S02, S10, S11.


#### CP-001. Подключить реальную доставку в Rust/WASM-пакете: завершить R1-B

**Тип:** GAP. **Зависимости:** P8; актуальный R1-B gap, если не закрыт при P7.

**Результат:** Назначенный hauling доставляет существующий cargo в warehouse этого поселения; задания используют реальные tool IDs через уже перенесённый WIT-контракт.

**Работа:** В портированном solaris-settlements проследить эквивалент JOB_WORK → WIT order → typed result → продолжение. Исходный main.lua служит historical reference, не целью дальнейшей разработки. Destination брать из существующего bound warehouse handle с проверкой ownership/readiness. Заменить category-like tool IDs конкретными предметами registry и согласовать с фактической выдачей kit. Сохранить направленность, повторяемый operation_id и прогресс; при изменении request_id не терять durable identity.

**Проверка:** Развернуть настоящий Rust component и полный пакет. **Граница:** Не переписывать CommitChest, не возвращать Luau module loader и не вводить другой router. Не требовать online-владельца, не давать бесплатные инструменты, не превращать допустимую частичную доставку в отказ всего cargo. Не расширять WIT, если перенесённый order уже выражает действие.


#### CP-002. Перепроверить readiness settlements на WASM и устранить сохранённый дефект

#### CP-005. Атомарно фиксировать одну строительную порцию

**Тип:** GAP. **Зависимости:** CP-004.

**Граница:** Не объявлять атомарным всё здание. Атомарная единица — документированная конечная portion. Не вводить отдельную construction saga поверх существующего журнала.


#### CP-006. Безопасно приостанавливать, отменять и возобновлять стройку

### B. Обычная Minecraft-игра, многопользовательское состояние и сохранения

### C. Общий API расширений и один клиентский контракт

Цель — реально исполнимые возможности для addons без специальных Rust-веток конкретного пакета. После P8 используется WIT + Rust SDK + mc-plugin-host, а ScriptBoundary, storage и Loader views/input/audio остаются прежними owners/adapters. Базовые возможности CP-030–036 уже обязательны в P-этапах; здесь закрывать только непокрытого потребителя/расширение, иначе verified-existing. Не откладывать сюда безопасность, ABI или reload миграции. Новые команды вводить только для отсутствующего действия конкретного потребителя. Источники: S03, S04, S11, S13.


#### CP-030. Проверить единый gameplay kernel для новых WIT-потребителей

**Тип:** VERIFY / TARGET для нового потребителя. **Зависимости:** P8, CP-029.

**Результат:** Выбранная обычная механика сохраняет одинаковые world/item правила для network и WASM инициатора, включая перенесённые precommit hooks.

**Работа:** Сверить evidence P2/P3/P5. На новой реальной inventory/block-edit вертикали пройти Rust guest → WIT → единственный DTO converter → ScriptBoundary/admission → owner. Удалить только обнаруженный duplicate planner/policy после перевода callers. Provenance выдаёт host; grants, игровые права и client consent независимы. Для действия с заявленным hook сохранить его общий precommit путь.

**Проверка:** Одинаковые исходные conditions через игрока и реальный component: accepted effect, отказ, stale revision, repeat в durable scope и observer. Прямые router ветви не доступны гостю. С нулём hook subscribers нет guest-wait, обязательную protection программный вызов не обходит.

**Граница:** Не создавать вторую boundary, ABI или общий action bus. Уже перенесённый P3 kernel не переписывается ради выполнения CP-030.


#### CP-031. Проверить результаты новых WASM-запросов без повторного request runtime

**Тип:** VERIFY / TARGET для нового потребителя. **Зависимости:** P8, CP-030.

**Результат:** Для активной операции различимы admission refusal, queued request, owner commit/окончательный отказ и внешняя доставка результата.

**Работа:** Переиспользовать P2/P3/P6 correlation, request budgets, outbox и generation/session fencing. Новая операция выдаёт результат следующей delivery-фазой без recursive callback. request_id коррелирует, operation_id используется только для предусмотренной durable semantics. Отключение Store не подменяет commit rollback; storage outcome остаётся доступным по существующему контракту.

**Проверка:** Overload admission, late result после disconnect/reload, required outbox full/closed, disabled receiver и committed operation без доставленного callback. Проверить bounded pending state и доступный authoritative outcome без обещания долговечности обычных in-memory events.

**Граница:** Не вводить новую workflow orchestration, второй outbox или exactly-once callbacks. Проверять только новый scope; применимые P3/P6 tests не переписывать.


#### CP-032. Сохранять устойчивые handles и bounded observations в новых WIT types

**Тип:** VERIFY / TARGET для нового потребителя. **Зависимости:** P8, CP-030, CP-031.

**Результат:** Новые entity/world/inventory запросы возвращают только разрешённые immutable values, а stale handles и unknown/unloaded состояние различимы.

**Работа:** Сверить P1/P3 handles. Разделить stable player identity, exact session, entity/plugin generation и object revision. Сохранить durable resident derivation; не экспортировать ECS/network IDs вместо неё. Новые WIT lists/strings проходят тот же safe pre-allocation decoder, aggregate byte budget и bounded pagination.

**Проверка:** Повторно занятый runtime ID, unload/reload, чужой namespace, изменение page roster, stale plugin generation и новая session. Для новых nested DTO повторить adversarial lengths/aliasing/NaN/Infinity tests; установить, сколько host copies реально допускается.

**Граница:** Не создавать глобальный registry-дубликат, синхронные world-read imports или snapshot всей карты. Идентификатор не доказывает право доступа.


#### CP-033. Проверить лимиты индуцированной работы новых плагинных API

**Тип:** VERIFY / TARGET для нового потребителя. **Зависимости:** P8, CP-031, CP-032.

**Результат:** Новая короткая guest-программа не запускает неограниченные scans, edits, navigation, entities, storage или output и не вытесняет здоровых игроков.

**Работа:** Переиспользовать обязательные P0/P2/P3 budgets. Для каждого нового вызова ограничить induced CPU/memory, DTO, retained snapshots, queues и outbound до дорогой работы. Fuel, epoch wall watchdog, native host cost и admission считать раздельно. Пул host-workers рассматривать только по измеренному bottleneck с сохранением последовательности callbacks каждого Store.

**Проверка:** Малый допустимый запрос рядом с flood/infinite guest, several plugins, filled consumers и event storm. Измерить bounded host/guest memory, очередь, fair rounds и latency здорового участника при сохранении accepted item decisions.

**Граница:** Не увеличивать guest fuel вместо исправления дорогого host API; не использовать timeout ожидания как остановку синхронного исполнения. Базовая безопасность не ждёт этого этапа: она обязательна до P8.


#### CP-034. Принять модульный Rust-пакет и самостоятельный SDK build

**Тип:** CONDITIONAL; прежний Luau module loader исключён. **Зависимости:** P8, CP-031, CP-033; конкретный расширяемый пакет.

**Результат:** Крупный реальный пакет собирает доменные Rust-модули через SDK в один проверенный component и выполняет выбранную новую игровую вертикаль.

**Работа:** Использовать структуру пакета и SDK из P1/P7. Вместе с необходимым функциональным расширением отделить затронутую бизнес-логику по обычным Rust-модулям, не меняя Store/state identity. Host и guest bindings берутся из одного WIT. Сохранить независимо воспроизводимую guest build и artifact hash; точные module names/команду брать из портированного проекта.

**Проверка:** Чистый отдельно собираемый SDK/package → component ABI validation → реальный gameplay прежней и новой вертикали. Модульный source не требует filesystem imports, серверной ECS/Wasmtime/Tokio-границы или пересборки core. Неверный WIT/export/dependency не даёт partial activation.

**Граница:** Не создавать startup require, dynamic module runtime, compiler внутри production server или второй Store на Rust-модуль. Один перенос файлов не закрывает checkpoint; при отсутствии функциональной необходимости оставить deferred/verified-existing.


#### CP-035. Распространить lifecycle и reload на новые plugin resources

**Тип:** VERIFY / TARGET для нового потребителя. **Зависимости:** P8, CP-031, CP-033.

**Результат:** Добавленные после миграции ресурсы/операции участвуют в уже обязательном P6 strict deployment reload, disable и host-owned cleanup.

**Работа:** Для каждого нового timer/subscription/registration/UI/pending request указать существующего owner и generation fence. Сохранить prepare-candidate → staged init → quiescent admitted-work resolution → atomic deployment routing switch → старый cleanup. Изменение grants, startup plan или client contract проверять на restart requirement; candidate memory входит в общий бюджет.

**Проверка:** Failure до switch сохраняет старый deployment; success не повторяет init-effects; старые timers/results не попадают в новую session/Store. Committed transfer остаётся определённым; shutdown trap не удаляет durable storage/residents/protection. Проверить обязательную защиту после disable.

**Граница:** Reload нельзя объявлять необязательным или откладывать из P6. Не переносить linear memory, не делать irreversible storage migration в init и не маскировать infrastructure failure изоляцией одного гостя.


#### CP-036. Замкнуть новую durable plugin-service операцию через WIT и существующий CAS

**Тип:** VERIFY / TARGET для нового потребителя. **Зависимости:** P8, CP-031, CP-035.

**Результат:** Rust-пакет сохраняет intent, узнаёт исход core operation и финализирует business state без повторного durable effect.

**Работа:** Для нового найма/оплаты/производства применить storage/CAS/receipts/status из P3, сохранив plugin IDs/keys и normal recovery. WIT не даёт прямого подключения к БД; namespace/grant и payload fingerprint проверяются host/owner. Срок retention определяет действующий recovery contract, не произвольный TTL.

**Проверка:** CAS conflict после core commit, same operation_id с иным payload, restart/reload между commit и финализацией, поздний result старому Store и bounded scan. Прочитать старые durable данные; exact effect count проверять для этой операции, а не приписывать всему ABI.

**Граница:** Не создавать новый ledger, saga DSL, WAL или outbox. DurabilityUnknown нельзя превращать в rollback и безусловный повтор выдачи items.


#### CP-037. Провести custom item через полный lifecycle

**Тип:** TARGET. **Зависимости:** CP-018, CP-020, CP-026, CP-030, CP-036.

**Результат:** Один настоящий пользовательский предмет сохраняет identity, компоненты и поведение от создания до save/drop/equipment/recipe.

Поведение не должно зависеть от того, каким vanilla carrier его рисует клиент. Native data остаются native data; guest configure выдаёт bounded contribution, а runtime WIT переносит только нужные values/handles. Правило повышения API версии следует отдельному контракту, не автоматически номеру item.

**Проверка:** Craft → stack split/merge → equip → combat/wear → drop/pickup → chest → restart; неправильная definition или отсутствующая capability явно отклоняется. Второй клиент видит тот же предмет.

**Граница:** Не считать переименованный vanilla sword полноценной custom item системой. Не добавлять enum на каждый предмет будущего каталога.


#### CP-038. Сверить handshake, schema и activation на трёх адаптерах

**Тип:** VERIFY. **Зависимости:** CP-035, CP-037.

**Результат:** Один согласованный bundle активируется на Fabric/NeoForge/Forge, а несовместимый клиент получает честный отказ.

### F. Завершить архитектурный cutover на реальных runtime-путях

Основная очередь ядра после C; её не требуется откладывать до всей ветки E. Основание — S04 и действующие ADR 0003–0009. Каждый пункт переносит ownership или изолирует реальную работу с наблюдаемым результатом. Перестановка файлов и создание crates сами по себе не закрывают этап.


#### CP-070. Запускать настоящую gameplay simulation без TCP

**Тип:** TARGET. **Зависимости:** CP-029, CP-043.

**Результат:** Тот же gameplay kernel, который обслуживает сервер, можно создать и вызвать из runtime-теста без socket/session fabrication.

**Проверка:** Один и тот же inventory/block/entity outcome через transport-free runtime и реальный клиент. Startup/check/production build не тянут siblings. Запрещённые операции отклоняются одинаково.

**Граница:** Не дублировать gameplay для удобного теста и не создавать crate на каждый глагол. До переноса callers не удалять действующий путь. mc-plugin-host остаётся отдельным runtime-адаптером без зависимости на mc-net; извлечение core не переносит guest execution в simulation.


#### CP-071. Довести ownership игрока независимо от connection state

**Тип:** TARGET. **Зависимости:** CP-018, CP-019, CP-027, CP-070.

**Результат:** Gameplay state игрока принадлежит simulation; соединение хранит только protocol/delivery/session информацию.

**Работа:** На оставшихся инвентарных/menu/pose путях перечислить реальные writable mirrors. Перевести callers на owner-committed state и сохранить клиентский baseline только для stale-protocol checks. Удалять старое поле лишь после миграции всех readers/writers.

**Проверка:** Hotbar, window/menu action, respawn, disconnect/reconnect, overlapping old/new session и competing addon mutation. Pending candidate не становится committed baseline до принятия owner.

**Граница:** Не удалять необходимый клиентский protocol baseline под лозунгом одной копии. Не расширять shared mutable player state глобальным mutex.


#### CP-072. Убрать блокирующие I/O из владельца simulation

**Тип:** TARGET. **Зависимости:** CP-026, CP-031, CP-070.

**Результат:** Disk/network/plugin callbacks не удерживают simulation owner; принятые долговременные операции сохраняют ясный commit contract.

**Работа:** На измеренном save/transaction пути отделить preparation, durable decision и asynchronous publication с существующими workers. Ограничить очередь и backpressure до принятия лишней работы. Отдельно определить, какое подтверждение требует дисковой долговечности. Не допускать блокирующие WASM imports и guest callbacks в owner; epochs/fuel не остановят зависший host I/O, поэтому исправлять его источник.

**Проверка:** Медленный disk/consumer, заполненная очередь, shutdown drain и recovery. Измерить owner-block time, сохранность accepted decisions и обслуживание здорового региона.

**Граница:** Не ослаблять durability ради TPS и не выдавать enqueue за durable commit. Не создавать ещё один storage buffer без одной понятной authority.


#### CP-073. Передавать пространственную ownership между регионами однократно

**Тип:** TARGET. **Зависимости:** CP-025, CP-028, CP-070, CP-071.

**Результат:** Игрок/сущность при переходе границы имеют одного writer и согласованную видимость, включая находящиеся в полёте запросы.

**Работа:** Проверить существующие leases/epochs/generation и handoff. Старые commands либо корректно маршрутизируются, либо явно отказываются; они не применяются к новому unrelated объекту. Определить один момент передачи и сохранность уже принятых effects.

**Проверка:** Переход туда-обратно, concurrent movement/action, stale compute result, disconnect и перегрузка принимающего региона. Два клиента наблюдают одну entity с корректным spawn/move lifecycle. Pending hook tickets и plugin results сохраняют независимость entity/plugin generation, session и object revision; stale не применяется к новому owner-объекту.

**Граница:** Не переносить region internals в plugin API. Не вводить распределённый cluster consensus для внутрипроцессного ownership.


#### CP-074. Валидировать результаты тяжёлого вычисления перед apply

**Тип:** TARGET. **Зависимости:** CP-024, CP-032, CP-033, CP-070, CP-073.

**Результат:** Worldgen/path/light preparation выполняется по immutable input и не перезаписывает изменившийся мир устаревшим результатом.

**Работа:** Взять реальный async compute путь с измеренной стоимостью. Определить snapshot/revision, bounded queue и owner-side validation. При stale result выбрать явный bounded отказ/перепланирование по событию; accepted mutation не теряется.

**Проверка:** Мир/target изменился в ходе вычисления, chunk unloaded/replaced, owner мигрировал, очередь насыщена. Проверить отсутствие stale overwrite, потерянного continuation и бесконечного retry.

**Граница:** Не копировать весь мир ради immutable view и не хранить долгоживущий mutable handle в worker. Не строить универсальный scheduler framework.


#### CP-075. Изолировать медленное соединение от commit и других игроков

**Тип:** TARGET. **Зависимости:** CP-025, CP-027, CP-031, CP-071, CP-072.

**Результат:** Медленный клиент не удерживает симуляцию и не заставляет терять обязательные результаты принятых действий.

**Работа:** Следовать существующему outbound-pressure ADR. Captured effects принадлежат принятому outcome; доставка имеет bounded ordered lane. Отличать допустимо заменяемые snapshots от обязательных transaction/lifecycle сообщений. Переполнение завершается явным исходом соединения.

**Проверка:** Один клиент перестал читать, другой играет; burst chunks + inventory ack + keepalive; disconnect после commit и reconnect. Проверить memory/queue limits и целостность view/entity lifecycle.

**Граница:** Не выбрасывать без разбора последние packets и не объявлять «последнее состояние всё исправит» для transaction receipts. Не включать бесконечный outbound buffer.


#### CP-076. Сохранить WASM-изоляцию после регионального cutover ядра

**Тип:** VERIFY / TARGET при найденном регрессе. **Зависимости:** P8, CP-030, CP-031, CP-033, CP-035, CP-070, CP-072.

**Результат:** Изменённое ядро по-прежнему обслуживает каждый plugin Store последовательными bounded callbacks вне spatial locks и не создаёт plugin-owned world state.

**Работа:** Сверить новую application/regional границу с P0–P8. Сохранить mc-script без runtime dependencies, один mc-plugin-host, один converter/admission/router и immutable observations. **Проверка:** Медленный/ошибочный гость рядом с корректным, full event/outbox queue, callback-generated mutation, precommit ticket через migration, completion после disable/reload. Здоровый игрок продолжает игру; memory/queue fences, items и protection остаются корректны.

**Граница:** Смена VM уже закрыта в P8; здесь не начинается новый runtime rewrite. Не создавать Store на region/entity, mc-extension boundary или вторую spatial authority; не дожидаться CP-076 для базовой WASM-безопасности.


#### CP-077. Закрыть реальный межрегионный составной commit

**Тип:** TARGET. **Зависимости:** CP-005, CP-030, CP-072, CP-073, CP-074, CP-076.

**Результат:** Одна нужная production-операция с несколькими владельцами либо принимается согласованно, либо явно отказывает без частичного эффекта.

**Работа:** Выбрать существующий кейс: ограниченная строительная portion, передача связанных participants или group admission. Использовать предусмотренную текущими ADR координацию только для этой границы. Зафиксировать ordering, participant fences и recovery decision.

**Проверка:** Один participant stale, migration между prepare/apply, capacity отказ и restart вокруг decision. Проверить все inventories/blocks/receipts и отсутствие утечки удерживаемого ownership.

**Граница:** Не оборачивать в multi-owner transaction всё движение/AI. Не маскировать распределённость последовательными success-записями и компенсирующим best-effort rollback.


#### CP-078. Принять архитектурный cutover без параллельных legacy-путей

**Тип:** VERIFY. **Зависимости:** CP-070, CP-071, CP-072, CP-073, CP-074, CP-075, CP-076, CP-077.

Проверить отсутствие второго production caller старого commit, не только отсутствие имени файла. Dependency/caller audit подтверждает, что mc-script остаётся runtime-независимым, Wasmtime живёт в mc-plugin-host, а Luau-path не возвращён рефакторингом.

### G. Производительность, ограничение нагрузки и R8 handoff

Оптимизация начинается с воспроизводимого измерения, а не выбора очередного cache или lock-free структуры. Product target из S03: 20 одновременных игроков, view distance 8, выше 18 TPS на 4-vCPU/8-GiB VPS. Это целевой сценарий, не текущая способность; более строгие существующие workload gates не ослабляются.


#### CP-079. Получить воспроизводимый performance baseline реальной игры

**Тип:** TARGET. **Зависимости:** CP-029, CP-043, CP-078.

**Результат:** Профиль связывает gameplay workload, time/queue/memory и фактический bottleneck на конкретной машине.

**Работа:** Переиспользовать profile.json и harness workloads; добавить только недостающие измерения, отвечающие конкретному вопросу. Зафиксировать hardware/cgroup, affinity, toolchain, build, seed, populations, warm/cold state и идентичность сценария. CPU sampling отделять от stage metrics. Luau/WASM baseline уже обязан существовать из P0/P7; здесь новый post-cutover профиль, не отложенная приёмка миграции. Отдельно измерять guest execution, host lifting/cleanup, induced native work, configure/compile и reload peak memory.

**Проверка:** Один полный неизменённый workload с распределениями latency/TPS, RSS, queue depth и lock wait. Неподготовленная среда и failed setup дают blocked/failure, не нулевую нагрузку как PASS.

**Граница:** Не оптимизировать до baseline и не выбирать результат одного удачного запуска. Число entities без их работы не измеряет AI/combat capacity.


#### CP-080. Ускорить измеренный worldgen/chunk bottleneck

**Результат:** Тот же cold/warm chunk workload обслуживается быстрее или с меньшей памятью без изменения принятой геометрии.

**Работа:** Из профиля выбрать один доминирующий расчёт/allocation/повторный доступ. Применить локальное переиспользование данных, batching или bounded cache с явной invalidation/removal границей. Сохранить generation contract и точность источников.

**Проверка:** Идентичный seed/region/population before/after, latency distribution, memory и world hash в заявленном deterministic scope; real-client streaming без нового blink. Отдельно cold и warm.

**Граница:** Если bottleneck не в worldgen, пункт не выполнять. Не менять terrain semantics, view distance или набор chunks ради графика.


#### CP-081. Ускорить измеренную стоимость lighting

**Тип:** CONDITIONAL. **Зависимости:** CP-022, CP-025, CP-074, CP-079.

**Результат:** Освещение для того же объёма edits/chunks сходится с меньшей стоимостью и без stale borders.

**Работа:** Локализовать duplicate recompute, frontier expansion или лишние копирования. Использовать текущую ownership и revision validation; объединять только работу с доказанно совместимой семантикой.

**Проверка:** Те же block edits, opaque/transparent transitions, chunk borders, unload/reload и динамические источники в scope. Compare final light и client view; измерить latency/allocations/queue.

**Граница:** Не отключать lighting и не считать уменьшение числа отправленных light packets доказательством ускорения расчёта.


#### CP-082. Снизить стоимость активного AI/pathfinding

**Тип:** CONDITIONAL. **Зависимости:** CP-033, CP-074, CP-079.

**Результат:** Заявленный активный roster движется/работает/сражается в заданном budget без подмены физической игры.

**Работа:** Измерить perception, queries, path expansion и повторную работу. Ограниченно переиспользовать результаты при действительных fences, обновлять по изменению мира/цели и simulation events. Дорогая работа получает честный local delay/admission.

**Проверка:** Движущиеся цели, obstacles, combat, worker jobs, region migration и наполненный roster. При тех же populations/assertions сравнить p95/p99, path work и наблюдаемое поведение.

**Граница:** Не заменять active agents idle entities, телепортацией или offscreen summary. Если military-ветка не активна, использовать реальные обычные mobs/jobs и отдельно не заявлять военный workload.


#### CP-083. Уменьшить contention инвентарей и мирового storage

**Тип:** CONDITIONAL. **Зависимости:** CP-019, CP-072, CP-077, CP-079.

**Проверка:** Два viewers + worker, параллельные независимые warehouses, save pressure и crossing-owner transfer. Throughput/latency вместе с conservation/stale-fence tests.

**Граница:** Не вводить DashMap/lock-free/ECS перестройку по вкусу. Не считать throughput без conflict-path корректности улучшением.


#### CP-084. Снизить стоимость сетевой публикации без потери семантики

**Тип:** CONDITIONAL. **Зависимости:** CP-025, CP-075, CP-079.

**Результат:** Тот же видимый мир доставляется с меньшими CPU/allocations/bytes и сохранённым transaction/lifecycle порядком.

**Работа:** Измерить encode/compress/copy и повторные snapshots. Применить ограниченный batching или переиспользование immutable bytes для реально совпадающих представлений. Не смешивать permission-scoped projections разных клиентов.

**Проверка:** Одинаковый view/population, fast+slow клиент, burst updates и inventory actions. Проверить spawn-before-delta, resync/ack и отсутствие утечек приватных данных; измерить CPU/RSS и latency.

**Граница:** Не переупорядочивать обязательные effects и не считать потерянные packets сетевой оптимизацией.


#### CP-085. Проверить capacity detection и предсказуемый autoscale

**Тип:** VERIFY. **Зависимости:** CP-033, CP-072, CP-075, CP-079.

**Граница:** Не добавлять operator worker-thread percentages. Не сокращать незаметно workload при проверке того же perf gate. Guest fuel, epoch interruption, host compilation и simulation admission — разные пределы; autoscale не делает fuel единицей времени и не отменяет per-plugin квоты.


#### CP-086. Подтвердить целевую мощность ядра и границы перегрузки

**Тип:** VERIFY. **Зависимости:** CP-079, CP-085.

**Результат:** Есть доказательство или точный отчёт о недостижении product target и неизменённых обязательных нагрузочных матриц.

**Граница:** Зависимости CP-080–084 активируются только для найденных bottlenecks. Отсутствие их патчей допустимо, отсутствие required evidence — нет. Более слабый VPS target не отменяет строгий living-world gate.


#### CP-087. Принять физический/стратегический handoff большой кампании

**Граница:** Не запускать эту систему ради экономии на обычном single-region survival. Не называть dormant accrual физической добычей и не обещать большой scale по маленькому тесту.

#### CP-089. Доказать storage recovery на настоящих аварийных границах

#### CP-090. Отказывать при дисковых и ресурсных сбоях без скрытой порчи

Для выбранного settlements scope включить реальные battle/caravan/registry workloads, а не отдельно idle server. Включить нормальный и ошибочный WASM guests, event storm, slow storage, повторный successful/failed strict reload и ограниченную память кандидатов. Здоровый пакет/игрок должен реально выполнять работу.

**Проверка:** Рост memory/queues/retained chunks, completed vs pending operations, item/identity balance, tick distributions и restart. На failures сохранить точный участок сценария. Завершение по пройденным assertions; elapsed time отдельно.

**Граница:** Не объявлять PASS потому, что процесс прожил N часов. Не считать валидной кампанию, у которой все workers стоят paused и не создают нагрузку.


#### CP-095. Свести текущую матрицу готовности с проверяемым denominator

**Тип:** VERIFY. **Зависимости:** CP-029, CP-043, CP-078, CP-086, CP-089, CP-094.

**Результат:** Каждое заявление о механике и мощности связано с точным evidence; неподтверждённые области явно остаются вне принятого scope.

**Работа:** Обновить существующий VALIDATION_LEDGER/DoD путями последних receipts и привязкой к final tree. Для vanilla coverage использовать зафиксированный in-scope denominator и нормальный runtime + отдельный oracle/client evidence. Контентные requirements считать отдельно от vanilla. Отдельно проверить всю WASM-матрицу P0–P8 и версии WIT/SDK/компонентов. Наличие нового runtime не увеличивает denominator vanilla parity и не заменяет сравнение P0/P7.

**Проверка:** Проверить source revisions, фактические assertions, skipped/prepared tests, failed owner scenarios и несовпадение workloads. Целевой порог 80% применяется по DoD, не вычисляется из произвольного списка зелёных тестов.

**Граница:** Не менять denominator ради достижения порога и не превращать старый M95 процент в текущее измерение. Это финальная проверка принятого результата, не новый competing readiness документ.


#### CP-096. Закрыть scoped release candidate и зафиксировать следующий продуктовый рубеж

**Тип:** VERIFY. **Зависимости:** CP-088, CP-089, CP-090, CP-091, CP-092, CP-093, CP-094, CP-095.

**Результат:** Есть проверенный кандидат с точными границами, установкой, backup/recovery и приёмкой владельца там, где она обязательна.

**Работа:** На конечных согласованных revisions выполнить обязательные release gates, сверить инструкции и known gaps. Для полного settlements релиза дополнительно требовать R0–R9, CP-069/087 и их evidence; для core кандидата честно ограничить scope. Подготовить changelog и handoff следующей задачи.

**Проверка:** Чистый install/run, no-debug gameplay, multiplayer, save/recovery, selected addon/Loader platforms, неизменённые perf workloads и owner field testing. Release-ready допускается только по реальному DoD выбранного scope. P8 принят, Luau execution/dependencies удалены из production; чужой внешний Rust component подключается без пересборки сервера и не обходит grants/decoding/staging limits.

**Граница:** Не пушить, не тегировать и не публиковать без отдельного разрешения. Незакрытый gate нельзя заменить обещанием проверить после релиза; статус остаётся draft/stabilization с точным blocker.

## 8. Первый рабочий пакет: P0, затем прежний R1-B на WASM

### 8.1 Вход и обязательный результат P0

**Вход:** фактический core HEAD, применимые инструкции, существующие примеры плагинов и новая WASM-спецификация.  
**Выход:** исполнимый Rust component, безопасно ограниченный ABI-прототип host, матрица переносимого API, зафиксированные dependency/toolchain версии и baseline receipts.  
**Не результат:** новый пустой crate, автоматически сгенерированные объявления WIT или таблица без запущенного компонента.

### 8.2 Один ограниченный discovery batch

1. Сверить HEAD/dirty tree. Сохранить старый R1-B cursor как pending-предметную работу; не терять уже сделанный owned diff и не возвращать старое решение сохранить Luau.
2. Прочитать текущие boundary/commands/events, Luau registrations, router, commit outbox и storage operations; выяснить production callers startup/reload/Loader. Не перебирать всю физику или большую campaign spec.
3. По реальным пакетам и tests составить матрицу: текущий callback/API → caller → grant/capability → новый WIT surface → owner/commit/result → durable semantics → test/потребитель. Пустое поле — конкретный непроверенный участок, а не автоматически отсутствующая функция.
4. Проверить совместимость выбранных стабильных Wasmtime/wit-bindgen/component tools с MSRV и server targets. Зафиксировать точные версии/команды/lockfiles; не задавать toolchain по памяти и не обновлять Loader вместе с host.
5. Установить, как выбранные bindings читают список/строку до host allocation. На конкретном safe API доказать bounded lifting nested/aliased данных. Одного post-decode `len()` недостаточно.

### 8.3 Исполнимая вертикаль

Собрать минимальный component с init, получением ограниченной event batch и возвратом command batch. Поднять ограниченный тестовый host с теми же предполагаемыми WIT/types и отдельным Store. До instantiation установить limits/fuel/epoch deadline; источник epoch — независимый от worker. Пройти callback и обязательный post-return, затем валидацию/staging. Не связывать небезопасный прототип с игровым owner.

Исходники компонентов и команды сборки оставить воспроизводимыми. Структуру прототипа согласовать с будущим единственным `mc-plugin-host`, не создавать permanent mini-runtime рядом. Полный SDK и перенос общей metadata — P1; обычный игрок — P2. P0 обязан выполнить собственные tests, а не обещать их более поздним этапам.

### 8.4 Приёмочная таблица P0

| Случай | Наблюдение, необходимое для закрытия |
|---|---|
| Корректный Rust component | Instantiation, init/event и декодированный ограниченный batch действительно исполнены. |
| Core module / неверный WIT / неизвестный import | Отказ до допуска в игровой host; совпавшая строка версии не обходит type check. |
| Infinite loop / trap в init или callback | Применимые механизмы останавливают guest; неопубликованный batch не имеет игровых effects. |
| Realloc/post-return/cleanup исчерпывает бюджет или падает | Публикации до обязательного завершения нет; guest memory не объявлена откатившейся. |
| Длина, вложенность, многократные ссылки на строки | Отказ до неограниченного раскрытия в host memory; учитывается суммарный объём копий. |
| Несколько memories/tables/instances и stack growth | Проверяются aggregate и per-resource пределы; ограничение одной linear memory недостаточно. |
| MSRV и Linux x86_64/AArch64 | Записаны фактически пройденные проверки либо точный blocker каждого target. |
| Старый host baseline | Сохранены workload/build/hardware/seed и tick/plugin/queue/CPU/RSS/error metrics, пригодные для сравнения в P7. |

Полная обязательная матрица миграции — [приложение A, §11][S18]; P0 закрывает только свой scope, остальное закреплено за P2–P7.

### 8.5 Завершение P0

Сохранить конкретные исходники/артефакты тестовой вертикали, матрицу API и receipts по существующим соглашениям. Обновить один cursor: версии toolchain, hash WIT/component, owned files, реальные команды, safety gate и следующий незавершённый P-этап. Новые файлы включить в tree fingerprint. Если safe bounded decoding или совместимость не доказаны, P0 остаётся `blocked`/`code_done`; не объявлять P2 безопасным. Независимое review отдельно от self-check. Git writes и production rollout без отдельного разрешения не выполнять.

### 8.6 Первый предметный пакет после P8: CP-001

Ниже сохранена детализация прежнего первого задания, но она исполняется в портированном Rust/WASM-пакете. `JOB_WORK`/`ROLE_KIT` обозначают исходные предметные понятия; фактические Rust symbols определяются по результатам P7. Исторический `main.lua` — только reference старого поведения, не целевой файл для нового функционального изменения.


#### 8.6.1 Контракт результата

**Вход:** существующее поселение, принятый resident, настоящий carry, привязанный склад и разрешённое hauling-задание.  
**Выход:** фактически перемещённые stacks в складском контейнере, точный остаток carry и согласованный статус задачи.  
**Нормальные отказы:** отсутствующий/непринадлежащий binding, недоступное состояние, отсутствие входа, отсутствие места и иные уже определённые доменные отказы. Названия error enum брать из текущего кода, не придумывать новые ради этого документа.

#### 8.6.2 Ограниченная разведка

1. Сверить свежий `resume.next` и owned diff. После принятого P8 проверить, не закрыт ли R1-B предметным исправлением в P7; при применимом evidence перейти дальше без повторного изменения.
2. Прочитать sibling AGENTS и портированную Rust-политику, соответствующую исходному `JOB_WORK`, поискать место, которое из `hauling` строит order. Установить, откуда там доступен warehouse handle и почему он должен принадлежать этому settlement.
3. Проследить один обработчик результата/продолжения: когда меняются operation id, progress и job status.
4. Найти существующий тестовый deployment helper, который копирует пакет целиком, и ближайший runtime scenario для вызова фактического Rust/WASM handler. Старые unit-тесты core deposit важны, но не доказывают, что WASM-компонент теперь формирует правильный order.

Этого достаточно для первого patch batch. Не начинать review всей физики, ECS, generation, Loader renderer или многотысячного каталога.

#### 8.6.3 Изменение

- Destination брать из действующего bound warehouse, а не первой попавшейся chest coordinate.
- Tool ids выбрать из реально загруженного registry и используемой production chain. Обновить связанные выдачу/проверку kit только там, где без этого активная задача не исполняется. Не создавать новые предметы и не давать инструменты бесплатно в production.
- Сохранить направление `source → destination`; endpoints не сортировать.
- После partial transfer оставить непоместившиеся stacks у работника и продолжить по текущим правилам, без обнуления cargo или повторного зачисления уже принятой части.
- Ошибка чтения binding не должна возвращать «пустой warehouse» и запускать альтернативный неавторитетный путь.
- Если core уже выражает нужный order, не расширять DTO/command variants.

#### 8.6.4 Минимальное предметное покрытие

| Случай | Обязательное наблюдение |
|---|---|
| Обычный job из shipped Rust component | Реальный core получил и исполнил directed order; содержимое chest изменилось. |
| Повтор того же завершения | Один transfer; новое начисление отсутствует. |
| Склад полностью заполнен | Ни один предмет не уничтожен; carry сохранён; объяснимый отказ. |
| Первый stack не помещается, второй помещается | Поздний stack переносится, непоместившийся остаётся; прогресс не откатывается. |
| Привязка недоступна/чужая/устарела | Нет чужого read/write и подмены результата пустым состоянием. |
| Перезапуск после commit | Carry/chest/order отражают один согласованный эффект. |
| Владельца игрока нет online | Нет выдуманного player principal; допустимость зависит от настоящих job/ownership правил. |
| Нужного инструмента нет | Нет бесплатной добычи; возвращается существующая причина остановки. |

Общие core tests из курсора — `worker_haul_deposits_its_cargo_into_the_bound_warehouse`, `a_full_container_leaves_the_cargo_with_the_worker`, `a_replayed_haul_deposits_once`, `a_haul_deposits_past_a_stack_the_container_refuses`. Они являются известными точками проверки на базе, а не гарантией неизменных имён после будущего refactor. Фильтр Cargo, запустивший **ноль тестов**, не даёт PASS задачи. [S02]

Один bounded diff в реально затронутом репозитории/репозиториях; focused shipped-package runtime test; применимый конечный L2; запись client acceptance как отложенной, если решение владельца всё ещё действует. Обновить cursor один раз. Не пушить автоматически. Следующий пункт — CP-002 либо уже назначенный актуальным курсором блокер, затем CP-003.

## 9. Как не утонуть в большом плане

### 9.1 Правила изменения очереди

При найденной потере items, нормального save, обходе разрешений или блокировке обычной игры: сохранить repro, обозначить blocker и закрыть минимальный связанный результат раньше следующего feature. Наличие старого открытого diff не даёт ему приоритет над такой ошибкой.

При найденном редком edge без нормального repro: записать точное условие в текущий owning item, не уходить в отдельную подсистему «защиты от всего». Дальняя идея не должна вытеснять активный P-этап миграции или выбранный CP-результат после неё.

Если API уже существует, проверить его production callers и accepted behavior. Тесты, docs или имена enum могут отставать; это не причина создать аналог. Если поведение существует, но доказательства нет, исправлять evidence gap, а не выдумывать code gap.

Смена WIT схемы проверяется конкретным потребителем и согласованными host/SDK/package revisions. Она не означает одновременное повышение Loader wire, storage format или world contract. Версии этих контрактов независимы. [S18] Удалять старую Solaris-схему после переноса; поддержка alpha backwards compatibility не подразумевается.

### 9.2 Триггеры остановки конкретного этапа

| Ситуация | Правильное действие |
|---|---|
| Неясна game-design цена/валюта/offline-war policy | Найти утверждённый контракт; если его нет и выбор материален, зафиксировать decision blocker и не выдумывать правила. |
| Bounded WIT decoding либо limits до instantiation не доказаны | Safety blocker P0/P2; не допускать component к игровому host, не подменять safe API собственным unsafe ABI. |
| Обязательный migration gate недоступен | Доступную независимую реализацию закончить, статус не повышать; P8/cutover остаются незакрытыми. |
| Неизвестен vanilla packet/layout | Получить exact local reference; до этого не писать guessed decoder/encoder. |
| Нет sibling для shipped-package integration | Продолжить доступную core часть, но integration оставить blocked; не подменять package mock. |
| Нет client jar/Java/Xvfb/token | Подготовить необходимые сценарии; code-level checks отдельно. Клиентский gate не выполнен. |
| Владелец отложил acceptance | Сохранить deferred_by_owner; план не отменяет его решение. |
| Нет write access | Подготовить patch/artifact и точный apply/test маршрут; не сообщать о внесённом изменении. |
| Независимый reviewer недоступен | Собственный отдельный review-pass; честная пометка independent_review not_run. |
| Performance workload не помещается на машине | Сохранить configured workload, среду и blocker. Малый probe допустим как отдельное доказательство, не вместо требуемого результата. |
| Нет разрешения на commit/push/tag | Сохранить owned diff и cursor; не выполнять Git write только ради завершения этапа. |

Один недоступный gate не означает, что все остальные задачи в пределах активного результата невозможны. Продолжать только независимую разрешённую работу; не считать неподтверждённую зависимость выполненной.

### 9.3 Признаки ложного прогресса

Не закрывать пункт, когда единственное новое свидетельство — больше LOC, больше enums, переставленные файлы, число названий API, принятый JSON, новый документ, сгенерированные заглушки, успешный `--check`, mock event, idle population или прошедшее время процесса.

Нужен факт уровня пользователя или владельца состояния: предмет перемещён, отказ ничего не изменил, новый клиент увидел верную entity, после restart восстановилась одна операция, здоровый клиент обслуживается при медленном соседе, тот же workload стал дешевле.

## 10. Передача между сессиями

### 10.1 Живой курсор

Вести его в текущем `docs/MEMORY.md`, не создавать новую параллельную систему памяти. Ниже шаблон содержимого, **не требование нового machine API**. Поля привести к существующему формату проекта.

```yaml
status: draft
checkpoint:
  id: P0
  outcome: "Real Rust component executes through a bounded WIT prototype"
  route: plugins
  primary_document: "<принятый путь этой спецификации / текущий docs/PLUGINS.md>"
  state: in_progress  # pending | in_progress | code_done | accepted | blocked | deferred

sources:
  core:
    base_commit: "<git rev-parse HEAD>"
    base_tree: "<git rev-parse HEAD^{tree}>"
  plugins:
    base_commit: "<реальная sibling revision>"
  loader:
    base_commit: "<revision, только если нужен этому результату>"

contracts:
  server_plugin_api: "solaris:plugin@0.7.0"
  wit_hash: "<фактический hash WIT; не версия Loader>"
  host_dependencies: "<закреплённые версии Wasmtime и bindings из P0>"
  guest_toolchain: "<проверенные версии и точная команда component build>"
  component_sha256: "<реальный артефакт, когда построен>"
  storage_schema: "<существующая версия; не повышать из-за VM>"
  loader_wire: "<реальная независимая версия>"
  world_contract: "<реальный effective plan; не hash WASM>"

owned_changes:
  - "<repo>:<path>"
diff_hash: "<hash diff + содержимого новых owned files>"

validation:
  - command: "<точная команда>"
    tree_fingerprint: "<проверенное дерево, включая новые файлы>"
    environment: "<необходимые версии/конфиг>"
    scope: "<что именно доказано>"
    result: "<passed | failed | prepared | interrupted | not_run>"
    receipt: "<существующий локальный путь result.json/log; не выдумывать>"
migration_safety_gate: not_run
client_acceptance: "<not_run | blocked | deferred_by_owner | passed; с отдельным scope>"
independent_review: not_run

blockers: []
known_gaps:
  - "<незакрытый результат, без преувеличения области>"
resume:
  next: "<одно действие с наблюдаемым результатом и требуемым evidence>"
```

`base_tree` и `base_commit` — разные Git objects. `diff_hash` только от `git diff` не покрывает новые untracked исходники: включить принадлежащие checkpoint новые файлы в fingerprint. Не включать туда гигабайты build artifacts и не называть unrelated изменения своими.

Для code_done с pending acceptance написать обе части явно. Не присваивать `accepted` автоматически из зелёного Rust. Совместимость трёх репозиториев фиксировать реальными ревизиями; core commit не определяет sibling содержимое.

### 10.2 Минимальный пакет контекста следующему агенту

Передать текущий outcome, route, base, owned files, важный production entrypoint, подтверждённую проблему, последний failed/passed receipt и одно следующее действие. Не передавать целиком историю P0–P8 и CP-001–096 и архивы диалогов. Сам каталог подгружать только вокруг нужной ветки.

После compaction не проводить discovery заново, пока рабочее дерево не изменилось по нужному scope. Перед повтором теста проверить validation identity. Завершённый checkpoint не должен переезжать в новый контекст как незавершённая бесконечная задача.

### 10.3 Итог одного checkpoint для владельца

```text
P<n> / CP-xxx — <наблюдаемый результат>. Зрелость: draft/stabilization/release-ready.
Изменено: <2–4 конкретных эффекта и реально затронутые repos>.
Проверено: <точные gates, количества/сценарии, итог, receipts>.
Не проверено/заблокировано: <только реальные ограничения>.
Git: <без коммита / локальный коммит SHA / явное отсутствие push>.
Далее: <один следующий конечный результат>.
```

Не писать владельцу каждую команду, запуск поиска или исправленную запятую. Сообщать выбранный результат, существенный blocker и итог со свидетельствами. Большой план не является разрешением на бесконечную фоновую работу без отчёта.

После P0–P8 и закрытия применимых CP-001–096 выбирать следующую цель из реального field testing, а не автоматически плодить новую архитектуру. ## Приложение A. Нормативная спецификация WASM / Wasmtime

### Solaris: перепроектирование плагинов на WASM / Wasmtime

#### Задание для DeepSeek

Переведи серверные плагины Solaris с Luau на **WebAssembly Component Model + Wasmtime**, с версионируемым WIT-контрактом и Rust SDK. Сохрани существующие игровые операции, владение состоянием, долговечность данных и Solaris Loader. Заверши переход удалением заменённого Luau-пути.

Работай по этапам ниже. Каждый этап заканчивается работающей вертикалью и проверками. Не ограничивайся созданием интерфейсов, пустых модулей или переписыванием документации. Не расширяй задачу до переписывания всего игрового ядра.

**Основание плана:** выборочное чтение `kaiserproger/solaris`, ветка `main`, коммит `b676669c02bcb4b4d5d886aa6f3b19ed2b072f17`, 16 сентября 2026 года. При подготовке документа код не изменялся, сборка и тесты не запускались. Реализация соседних репозиториев целиком не проверялась.

Перед изменениями проверь текущий HEAD и незакоммиченные изменения. Отличия от указанного коммита учитывай адресно; не откатывай чужую работу.

#### 1. От чего отталкиваться

В Solaris уже есть значительная часть нужной архитектуры. Её следует переиспользовать.

| Проверенная часть | Что учитывать при переходе |
| --- | --- |
| `mc-script` | Уже содержит события-снимки, ограниченные команды, capabilities, admission и `ScriptBoundary`. Новый транспорт не должен создавать вторую границу полномочий. [R1] |
| `mc-script/src/lua.rs` | Luau работает с отдельной VM на плагин, на выделенном host-потоке; заданы ограничения памяти, исполнения, очередей и таймеров. Замена VM сама по себе не является доказательством улучшения изоляции или производительности. [R2] |

#### 2. Зафиксированные решения

**Конечный серверный runtime один: Wasmtime.** Не поддерживать одновременно Luau, WASM, нативные `.so`/`.dll` и универсальный выбор движка. На промежуточных этапах старый host может оставаться для сравнительных тестов; один production deployment не запускает два пути.

**Публичный ABI — WIT.** Rust ABI, `Box<dyn Plugin>`, структуры ECS и внутренние типы движка не становятся контрактом пакета. WIT описывает интерфейсы и типы; семантику исполнения, отказов и совместимости нужно зафиксировать отдельно. [W1]

**Мир изменяет существующий владелец.** Плагин получает значения и формирует ограниченные команды. Применение идёт через существующий admission и игровые операции. Никаких `&mut World`, указателей, локов, региональных ключей, подключения к БД или обхода инвентарных транзакций.

**Гостевой код не выполняется на потоке владельца симуляции.** Это уточнение исходной общей идеи синхронных hooks под реальную архитектуру Solaris. Отменяемые действия реализуются как ограниченное решение до commit, без ожидания WASM под world/region lock. [R7]

**Область изоляции — экземпляр плагина в серверном runtime.** На первом этапе один `Store` на плагин и последовательные callbacks. Не создавать копию плагина на каждую сущность, chunk или регион: это размножит состояние и сломает существующие глобальные сервисы плагинов.

**Смена VM не меняет клиентскую платформу.** Сохранить существующий Solaris Loader и разделение server-only / Loader-required. Не переносить серверный WASM на Java-клиент и не добавлять второй клиентский runtime.

#### 3. Разделение кода без лишних крейтов

Добавить один runtime-крейт — `crates/mc-plugin-host`. Сохранить `mc-script` как runtime-независимую серверную границу. Его переименование не требуется.

| Место | Ответственность после перехода |
| --- | --- |
| `crates/mc-script` | Внутренние DTO, проверенные значения, capabilities, manifest-контракт, `ScriptBoundary`, admission, generation fences, ограниченные очереди и семантика результатов. Без `mlua`, `luaur` и Wasmtime. |
| `crates/mc-script/wit/` — новое | Единственный источник публичной схемы API. Разделение по нескольким реальным областям: lifecycle, events, commands, storage, presentation. |
| `crates/mc-plugin-host` — новое | Обнаружение пакетов, компиляция компонентов, Wasmtime, исполнение callbacks, квоты, преобразование WIT ↔ внутренние DTO, lifecycle и reload. |
| `crates/mc-net/src/script/` | Существующие адаптеры к игровым владельцам, storage, sessions и Loader. Не добавлять параллельный `wasm_router`. |
| `crates/mc-server` | Composition root: конфигурация, подготовка и запуск host, связывание с сервером, check/reload/shutdown. |
| `sdk/rust/` — новое | Отдельно собираемый guest SDK, использующий WIT. Не зависит от `mc-net`, Tokio-границы сервера, ECS или Wasmtime. |

Зависимости: host использует `mc-script`; сервер связывает host с `mc-net`; `mc-net` продолжает использовать runtime-независимую границу. Host не получает зависимость на игровые реализации `mc-net`.

Из `lua.rs` извлечь общие metadata-типы клиентских пакетов, startup rules и deployment. Назвать их без `Lua` там, где они больше не связаны с языком. Сохранить существующие поля и проверки. Разделение большого `lib.rs` выполнять по затронутой ответственности, без массовых механических переносов.

Не вводить новый универсальный `RuntimeProvider`, DI-контейнер, шину сообщений или фреймворк state machine. Существующий `ScriptRuntime` оценить по реальным вызывающим: не сохранять публичную полиморфную иерархию только ради уже удалённого второго runtime.

#### 4. Публичный контракт

##### 4.1. Версии и сборка

Начальная версия нового контракта — **`solaris:plugin@0.7.0`**. Это выбранная версия миграции, не уже существующая возможность репозитория. Manifest должен запрашивать точную версию; компонент должен соответствовать её WIT-типам и экспортам. Проверки строки `api` недостаточно.

Версии API, пакета, формата plugin storage, Loader wire protocol и world contract независимы. Не повышать их все одновременно из-за смены VM.

Rust SDK и host bindings используют один WIT. Не писать вручную вторую копию публичных структур для SDK. Преобразования во внутренние проверенные DTO остаются явными и находятся в одном месте.

На этапе P0 выбрать и закрепить совместимые стабильные версии Wasmtime, `wit-bindgen` и инструментов сборки компонентов. Проверить MSRV и Linux x86_64/AArch64. Документация `latest`/development не считается версией зависимости. Не обновлять Rust или Loader без установленной необходимости.

Сохранить `unsafe_code = "forbid"` для серверных крейтов. Не ослаблять lint ради собственного FFI или загрузки native-кеша.

Guest-пакет должен собираться в **component**, а не просто в core WASM module. Собрать один настоящий Rust-плагин и проверить его импорты. Не подключать весь WASI ради удобства стандартной библиотеки: исходный профиль работает без файлов, сети и окружения.

##### 4.2. Вызовы

Зафиксировать следующую семантику; точные WIT-объявления реализовать и проверить компилятором:

| Вызов | Семантика |
| --- | --- |
| `configure(config)` | Чистая startup-фаза, возвращает типизированный `StartupContribution`. Нет доступа к миру и runtime-командам. |
| `init(config, context)` | Инициализация runtime; возвращает staging batch. Это единственная точка стартового callback, без повторного запуска той же логики через дополнительный `server.started`. |
| `on-events(events)` | Ограниченная пачка immutable-событий → ограниченная пачка типизированных команд. |
| `before-build(context)` | Решение по ещё не совершённому строительному действию: `Keep` или `Cancel`. Подключается в P5. |
| `before-damage(context)` | `Keep`, `Cancel` или `Replace(amount)`. Подключается отдельной вертикалью в P5. |
| `shutdown()` | Ограниченный best-effort callback без обещания выполнения при аварии. Долговечность данных от него не зависит. |

Публичные имена событий и методов внутри версии единообразны. Старые Luau callbacks сопоставляются новым событиям в миграционной матрице; не держать постоянно два словаря.

Импорты хоста ограничить логированием и чтением уже подготовленного контекста вызова. Новые запросы к миру, storage и внешним сервисам проходят командами и результатами. Не выдавать синхронный `get_player`, который внутри захватывает session/world lock или ждёт chunk load.

WIT не должен экспортировать внутренние варианты `HostAttached`, `AdmittedScriptCommand` и поля, позволяющие гостю выбрать авторизующий `plugin_id` или поколение host.

##### 4.3. Идентификаторы и валидация

Разделить устойчивую идентичность игрока и ссылку на конкретную сессию. Сообщение, меню или клиентская команда для старой сессии не должны попадать в новую после reconnect.

Использовать проверяемые ссылки на сущности с поколением; координаты привязывать к конкретному миру. Поколение runtime-плагина, поколение сущности и revision игрового объекта имеют разные назначения. Не заменять их одним счётчиком.

Сохранить существующие durable resident handles и их derivation, пока нет отдельной миграции данных. Сырые ECS Entity и повторно используемые network entity ID в API не отдавать.

На границе проверять размеры, диапазоны, допустимые identifiers, конечность float, отрицательные количества, переполнения и вложенность. `NaN` и бесконечности в координатах, уроне и параметрах презентации отклонять. Наличие идентификатора не доказывает право на объект.

#### 5. Команды, результаты и единственное место применения

##### 5.1. Выполнение callback

До возврата из callback все его команды принадлежат локальному staging batch. Логирование допускается как ограниченный диагностический эффект; world/storage mutations, таймеры и регистрации не применяются немедленно.

После возврата host проверяет весь batch: корректность DTO, размер, число команд, разрешения и доступную admission-квоту. Только затем передаёт его существующей границе. Использовать имеющиеся `CommandBatch` и admission-механизмы, исправляя выявленные недостатки на месте. [R1], [R2]

Trap, исчерпание бюджета, ошибка декодирования или нарушение контракта отменяют **неопубликованный batch данного вызова**. Изменённую память гостя не считать откатившейся: неисправный экземпляр отключается.

Принятие batch не означает атомарность всех его игровых действий. Каждая команда повторно проверяется владельцем перед применением. Связанные изменения выполняются отдельной существующей атомарной операцией — например, inventory/storage transaction или storage batch CAS. Не превращать произвольную пачку телепортов, сообщений и операций над миром в общую транзакцию.

##### 5.2. Полномочия

Разрешённые возможности вычисляются из запроса пакета и явного разрешения администратора. В production отсутствие нужного grant — ошибка admission пакета, а не молчаливое урезание его поведения.

Проверять полномочия при приёме команды и её окончательном применении. Привязку к экземпляру создаёт host из состояния `Store`; гость её не предоставляет. Сохранить provenance действия: сетевой пользователь, системная работа и авторизованный плагин различимы.

Не смешивать три независимые проверки: права плагина на серверный API, права игрока на игровое действие и согласие клиента на возможности Loader. Плагин не получает право обходить protection только потому, что изменяет блок программно. Для действительно необходимого обхода требуется отдельное явное полномочие.

В `router.rs` проверить все точки входа. WASM-команды обязаны проходить авторизованный путь, включая chat/broadcast/disconnect. Наличие старого прямого пути для доверенной внутренней работы не должно давать гостю такой доступ. [R3]

##### 5.3. Результаты и долговечность

В API различать:

- отклонение до admission;
- принятие к выполнению;
- owner commit либо окончательное отклонение;
- внешнюю доставку результата, включая socket/Loader delivery.

Корреляция — через `request_id`; долговечная идентичность операции — через существующий `operation_id`, где этот контракт уже реализован. Повтор операции с тем же ID и иным содержимым должен давать конфликт. Не обещать exactly-once для каждой команды или callback. [R5]

Не переписывать существующие WAL/receipts, CAS, inventory fences и обработку `DurabilityUnknown` под новый runtime. После неопределённого исхода нельзя безусловно повторять выдачу предметов или сообщать об откате.

Сохранить `ScriptCommitEventOutbox` и его fail-closed сигнализацию. Не добавлять второй конкурирующий outbox. При расширении доставки резервировать необходимую ёмкость до новых необратимых изменений там, где это возможно; уже совершённый commit нельзя объявлять несовершившимся из-за ошибки очереди. [R4]

#### 6. Исполнение, порядок и отменяемые действия

##### 6.1. Host

Первый вариант использует один выделенный host-worker с отдельными Store и ограниченным последовательным исполнением. Это сохраняет понятную модель текущего host. Один общий `Engine` и неизменяемые скомпилированные компоненты можно переиспользовать; состояние гостей не разделяется.

Очереди и учёт работы — по плагинам, с общим серверным пределом. Обработчик одного плагина не получает бесконечную долю worker. Установить ограниченную порцию работы на scheduling round и проверяемый порядок обхода. Пул worker добавлять только после измерения конкретного bottleneck, без изменения последовательности callbacks одного экземпляра.

События несут tick и последовательность соответствующего владельца/потока событий. Фиксируется порядок доставки одному плагину и порядок handlers одного решения. Не обещать глобальный детерминизм всех регионов без специального механизма и тестов.

Результаты команд обрабатываются следующей фазой/доставкой, без рекурсивного повторного входа в плагин. Цепочки событий ограничиваются бюджетом, очередями и числом порождённых запросов. Никаких неограниченных автоматических retry.

##### 6.2. `before-build` и `before-damage`

Существующие декларативные защищённые зоны сохранить: для обычной проверки территории не нужен новый вызов WASM. Dynamic hooks добавляются только в действия, где есть зарегистрированный handler.

Для них реализовать один ограниченный precommit-путь:

1. Игровой владелец проверяет базовую допустимость, формирует immutable context и внутренний ticket с revisions. Действие ещё не совершено; предметы не списаны, урон не нанесён.
2. Работа поступает host. Владелец освобождает управление и продолжает другие действия; ожидание callback под локом запрещено.
3. Host вызывает handlers последовательно в фиксированном порядке администратора с `plugin_id` как однозначным tie-breaker. Общий deadline включает ожидание в очереди и всю цепочку.
4. Следующий damage-handler получает уже изменённую величину. `Cancel` окончателен; `Keep` не отменяет более ранний запрет.
5. Владелец принимает результат только для живого ticket, актуальных revisions, действующей сессии и разрешений. Затем выполняет обычную игровую операцию либо возвращает типизированный отказ.

Ticket ограничен временем жизни и ёмкостью очереди. Просроченное решение не применяется, повтор не выполняет действие ещё раз. Изменившиеся предусловия дают `Stale`, без бесконечной повторной проверки.

У hook нет доступа к мутациям, внешнему I/O и новым асинхронным запросам. Он читает переданный контекст и своё локальное состояние. Все источники того действия, которое API обещает перехватывать, должны проходить одну проверку; нельзя защитить только сетевую команду и оставить программный обход.

Обязательность hook и отказная политика определяются оператором. При отказе обязательной защиты действие запрещается. Отключение Store не удаляет защитную регистрацию и не открывает территорию. Осознанное снятие защиты администратором — отдельное действие.

Такой hook может добавить задержку между запросом и commit. Измерить её на реальном клиенте; не обещать нулевую задержку или исполнение в том же тике. При отсутствии подписчиков прямой игровой путь остаётся без WASM-ожидания.

#### 7. Ограничения ресурсов и безопасная граница WASM

Wasmtime предоставляет sandbox и механизмы ограничения исполнения, но корректность host API, memory accounting и игровые ограничения остаются ответственностью Solaris. Sandbox не равен изоляции отдельным процессом. [W2]

| Ресурс | Обязательное ограничение |
| --- | --- |
| Guest CPU | Fuel на вызов, общий бюджет плагина и host; отдельно wall-time watchdog через epoch interruption. Fuel не измеряется в миллисекундах. [W3] |
| Guest memory | Число и размер linear memories, таблиц и core instances внутри компонента, stack budget. `memory_size` применяется к каждой памяти отдельно. [W4] |
| Host memory | Размер входных/выходных DTO, очередей, удерживаемых snapshots, compiled components и временных буферов декодирования. |
| Индуцированная работа | Число команд, размер world edits, объём сканирования, пути/сущности, результаты запросов, storage bytes и outbound data. |
| Lifecycle | Бюджеты instantiation, configure/init, hook, shutdown, reload-кандидата и всех исполняемых guest cleanup-функций. |
| Диагностика | Частота и байты логов, длина ошибок/backtrace, ограниченная кардинальность метрик. |

Limits, fuel и epoch deadline устанавливаются **до instantiation**, поскольку исполняемый guest-код может присутствовать уже в инициализации компонента. Учитывать также `realloc` и `post-return`; staging batch нельзя опубликовать раньше завершения обязательной guest cleanup-фазы.

Epoch-counter обновляет независимый таймерный источник, который не блокируется тем же worker. Не использовать `sleep` в игровом цикле и не считать `tokio::time::timeout` вокруг синхронного вызова способом остановить его. Fuel/epochs не останавливают зависший host call: все imports должны иметь ограниченную стоимость и не выполнять блокирующий I/O. [W5]

**Проверка размера после автоматического создания гигантского `Vec`/`String` недостаточна.** На P0 проверить lifting выбранных bindings. Для выходных списков использовать безопасное ленивое чтение с проверкой количества до обхода и копирования; nested lists и повторно ссылающиеся строки также считать по итоговому объёму host-копий.

В Wasmtime существуют `WasmList` и `WasmStr`, но их нельзя автоматически считать совместимыми с любым сгенерированным binding. Нужен ограниченный decoder на поддерживаемых safe API либо другая доказанно ограниченная форма того же WIT-контракта. Не писать собственный unsafe ABI. Пока тест на вредоносные длины/вложенность не пройден, компонент не допускается к игровому host. [W6], [W8]

Компиляция `Component` является host-работой и не ограничивается guest fuel. Ограничить размер артефакта, количество пакетов, структуру принимаемого компонента и параллельную компиляцию. Компилировать до активации, вне симуляции. Не обещать, что отмена ожидания остановила уже запущенную компиляцию.

Принимать проверяемый WASM binary, не скачанный native/precompiled cache. Не использовать `Component::deserialize` на произвольном содержимом пакета: этот API имеет unsafe-контракт. В первом варианте собственный дисковый AOT-cache не нужен. [W7]

Начальные численные бюджеты определить по baseline и двум реальным Rust-плагинам. Сохранить существующие ограничения игровых DTO, если они не меняются по отдельному обоснованию. Текущие Luau fuel и 16 MiB не переносить механически в Wasmtime: единицы учёта и накладные расходы различаются. [R2]

#### 8. Пакеты, startup rules и клиентский контракт

##### 8.1. Формат пакета

Целевой минимальный пакет: `plugin.toml`, `plugin.wasm`, необязательный `config.toml` и существующие декларативные клиентские/контентные ресурсы.

Пример **нового**, подлежащего реализации manifest:

```toml
id = "hello"
name = "Hello"
version = "0.1.0"
api = "0.7.0"
entry = "plugin.wasm"
events = ["player.joined"]
capabilities = ["chat.send"]
player_commands = ["hello"]
```

Сохранить `[plugins].directory`, `strict` и `expected`. Добавить явные operator grants, например:

```toml
[plugins]
directory = "plugins"
strict = true
expected = ["hello"]

[plugins.grants.hello]
capabilities = ["chat.send"]
```

Это один словарь capabilities с единым смыслом. Сопоставление старых имён и новых разрешений выполняется при миграции пакетов, не runtime-алиасами навсегда.

Проверять обход путей, выход symlink за корень пакета, размеры файлов, неизвестные поля, повтор ID, конфликты команд и циклы реальных startup-зависимостей. Гость не имеет права читать каталог пакета самостоятельно.

`--check` проверяет весь выбранный deployment, ABI, imports, startup contributions и init с подавлением игровых эффектов. Не создаёт игровой мир, не меняет storage и не открывает listener. Декларативно значимый некорректный пакет не должен молча исчезать даже в permissive-режиме. [R6], [R8]

##### 8.2. Замена `rules.lua`

Существующий `rules.lua` — отдельная startup-only фаза, влияющая на native rule plan и world contract. Её нельзя удалить вместе с VM без замены. [R6]

Перенести вычисление в `configure(config) -> StartupContribution` того же WASM-компонента. Выполнять его в отдельном краткоживущем Store с пустыми runtime-возможностями. Передавать результат существующим валидаторам и `StartupData`.

Нормализованный результат должен сохранять существующий смысл worldgen/gameplay rules. Смена бинарника или компилятора при идентичном эффективном плане не должна сама по себе инвалидировать мир. Реальное несовместимое изменение правил продолжает отклоняться существующим world-contract gate. Не удалять контракт мира и не требовать новый мир только ради смены языка.

После переноса всех выбранных пакетов `rules.lua` больше не исполняется. Не оставлять скрытый Luau-runtime исключительно для startup.

##### 8.3. Loader

Сохранить metadata клиентских bundles, проверку размеров/хешей, negotiation, permissions и exact-session fencing. Типизированные WASM-команды используют уже существующую доставку UI/HUD, звука, payload и объявленного контента.

Server-only пакет не требует Loader. Пакет с клиентскими требованиями не получает фиктивную server-only замену. Изменение серверного ABI не является причиной повышать Loader wire protocol или переписывать Fabric/NeoForge/Forge adapters.

First-party пакеты остаются в `../solaris-default-plugins`, клиентский код — в `../solaris-loader`. Не возвращать их копии в ядро и не делать production-сборку ядра зависимой от наличия соседних checkout. [R10]

#### 9. Lifecycle, reload и отказ

##### 9.1. Отключение экземпляра

Host владеет подписками, таймерами, command registrations, временными клиентскими ресурсами и pending requests экземпляра. Очистка не зависит от успешного `shutdown()`.

Поздние результаты проверяются по generation и session fences. При смене поколения они не становятся ответами нового экземпляра. Для уже принятой долговечной операции сохраняется возможность узнать результат через storage-контракт.

Не удалять durable storage, resident identity и сохранённые protection rules при trap. Временный UI можно закрыть, но защита обязательного scope остаётся fail-closed. Различать отказ гостя и отказ обязательной инфраструктуры доставки/хранилища: второй нельзя маскировать отключением одного плагина.

Автоматический бесконечный перезапуск неисправных пакетов не добавлять.

##### 9.2. Горячая замена

Сохранить смысл существующего strict SIGHUP-reload, а не объявлять его ненужным после смены VM. Текущий контракт уже допускает замену кода/config при неизменных идентичностях, командах, worldgen и client bundles. [R6]

Реализовать последовательность:

1. Проверить и скомпилировать весь кандидатный deployment вне действующих Store.
2. Проверить идентичности, порядок, владение командами, startup contributions, клиентские договорённости и effective grants. Изменение этих контрактов требует рестарта.
3. Создать кандидатные Store, выполнить init со staging без видимых внешних эффектов.
4. На безопасной границе перестать выдавать старым экземплярам новые callbacks. Довести уже admitted операции до определённого исхода либо явно отклонить ещё не совершённые; не терять commits и required results.
5. Атомарно для deployment переключить маршрутизацию и поколения, затем разрешить кандидатные эффекты.
6. Освободить старые временные ресурсы. При неуспехе до переключения старый deployment остаётся действующим.

Учитывать память старых и кандидатных Store одновременно. При нехватке reload-бюджета отклонять замену, а не доводить процесс до OOM.

В первой WASM-версии сохранить существующую семантику: globals и таймеры после успешного reload начинаются заново, durable storage остаётся. Произвольное перенесение линейной памяти запрещено. `save-state/load-state` с отдельной версией схемы — последующее расширение, не условие базовой миграции.

В init/reload не выполнять необратимую миграцию storage. Перенос формата долговечных данных требует отдельной проверяемой процедуры; откат гостевого кода не является откатом данных.

#### 10. Этапы реализации

##### P0. Проверенная база и исполнимый ABI-прототип

**Сделать:** прочитать актуальные `AGENTS.md`, `docs/ARCHITECTURE.md`, `docs/PLUGINS.md` и текущий cursor. Собрать матрицу реально вызываемых API из `ScriptCommand`, `ScriptEvent`, регистрации Luau-функций, router и тестов. Для каждой возможности указать caller, capability, commit/result path и пакет-потребитель.

Зафиксировать baseline host без плагинов и с существующими примерами. Собрать минимальный Rust component на выбранной toolchain; проверить init, события, batch, ограниченное декодирование и trap. Согласовать изменения архитектурной документации с этим заданием: новая задача заменяет прежнее решение «сохранить Luau», остальные инварианты сохраняются.

**Приёмка:** реальные component bytes загружаются в тестовый host; несовместимый ABI отвергается; ограничения работают до instantiation; есть результаты проверок MSRV и target-совместимости. Не оставлять весь P0 набором документов без исполняемого прототипа.

##### P1. Отделение контракта от Luau

**Сделать:** создать `mc-plugin-host`, вынести runtime-независимые metadata и затронутые contract-модули из `lua.rs`. Добавить WIT и guest SDK. Существующие игровые значения, boundary и mutation adapters сохранить.

**Приёмка:** прежние тесты границы не потеряны; host не зависит от `mc-net`; SDK собирается отдельно; нет второго command router и дублированной публичной схемы. Временное существование старого host отмечено как миграционное, с этапом удаления P8.

##### P2. Настоящий WASM-плагин в сервере

**Сделать:** реализовать discovery, grants, strict/expected, `--check`, инстанцирование, serial callbacks, staging, budgets и диагностику. Подключить host к существующему `ScriptBoundary` из composition root.

Два первых сценария: приветствие при входе и команда `/hello`. Это тестовые server-only пакеты, не автоматически включаемые встроенные production-плагины.

**Приёмка:** обычный Minecraft-клиент получает ожидаемый ответ; неверный grant/ABI/manifest останавливает strict startup; trap одного гостя не ломает второй; `--check` не оставляет world/storage effects; ни одна гостевая команда не обходит admission.

##### P3. Существующие операции и данные

**Сделать:** перенести по матрице messaging, timers, queries, entity/world mutations, zones, teleport, storage/CAS, inventory и typed operation results. Затем закрыть реально используемые resident/settlement/order возможности, не добавляя новых доменных подсистем.

Переиспользовать существующие операции и validators. Тесты поведения переносить на реальные WASM-компоненты, сохраняя исходные утверждения. Не заменять функциональность заглушкой `unsupported` ради быстрого удаления Luau.

**Приёмка:** для каждой старой используемой возможности есть новый вызов, авторизация, результат и тест. Storage старого deployment читается после runtime-перехода; повторы операций, CAS-конфликты и item conservation проверены. Required outbox не превратился в best-effort очередь.

##### P4. Startup и Loader без смены платформы

**Сделать:** реализовать `configure`, перенести startup data metadata, интегрировать с `startup_rules`/`StartupData`/world validation. Провести client presentation и другие реально используемые Loader-команды через новый ABI.

**Приёмка:** одинаковый нормализованный startup plan не меняет world contract; изменённый несовместимый план отклоняется. Server-only сценарий работает без Loader. Реальный Loader-required fixture проходит предусмотренные платформенные проверки; отсутствие клиента или артефактов фиксируется как blocker, не как PASS.

##### P5. Ограниченные precommit hooks

**Сделать:** сначала `before-build` с `Keep/Cancel`, затем `before-damage` с изменением величины. Использовать протокол раздела 6.2 и те же игровые kernels. Не добавлять синхронный вызов Store из владельца симуляции.

**Приёмка:** два handlers имеют фиксированный порядок; поздний, повторный и устаревший ответы не меняют мир; trap обязательного handler не открывает защиту; cancel не расходует предмет и не наносит урон; программные действия не обходят заявленный hook. Измерены latency и отсутствие лишнего пути при нуле подписчиков.

##### P6. Reload, shutdown и ресурсная очистка

**Сделать:** реализовать безопасную замену deployment, generations, обработку admitted/committed работы и очистку временных ресурсов. Протестировать отказ в каждой существенной фазе кандидата.

**Приёмка:** неуспешный reload оставляет старый deployment; успешный не дублирует init-effects; старые timers/results не влияют на новый Store; durable операции и защитные правила сохраняются; кандидат не превышает общий memory budget.

##### P7. First-party пакеты и интеграционные gates

**Сделать:** проверить и портировать пакеты, реально используемые тестами и выбранным deployment, в `solaris-default-plugins`. Включить стандартный pack, его зависимости и startup/Loader-пакеты из матрицы P0. Сохранить plugin IDs и storage keys, если отдельная миграция не нужна.

Для соседнего репозитория вести отдельный diff и соблюдать его инструкции. При отсутствии checkout не создавать копию пакета в ядре: закончить доступную работу и явно оставить пакетный gate заблокированным.

Добавить воспроизводимую сборку SDK/fixtures в существующий harness и CI. Core production build не должен запускать guest compiler или требовать соседние репозитории. Unit-тесты используют fixtures с проверяемым исходником; отсутствие обязательного fixture не превращается в skip/pass.

**Приёмка:** существующие `plugin_examples`, `plugin_standard_pack` и необходимые клиентские сценарии выполняются через WASM с прежними проверками поведения. Набор переносимых API не сокращён ради зелёного теста.

##### P8. Единственный production-путь и удаление Luau

**Сделать:** переключить startup на новый host после завершения предыдущих gates. Удалить исполнение `main.lua`/`rules.lua`, Luau bindings/prelude, `lua-runtime`, ненужные `mlua`/`luaur`, старые entrypoints и временные переключатели.

Проверить workspace, CI, harness, installer, example config, test fixtures и документацию на действующие ссылки на старый runtime. Исторические evidence не переписывать. `AGENTS.md`, `ARCHITECTURE.md` и `PLUGINS.md` должны описывать один актуальный контракт, без конкурирующего плана.

**Приёмка:** WASM — единственный production-runtime; core собирается самостоятельно; новый пакет подключается без пересборки сервера; использованные раньше сценарии покрыты; нет runtime-адаптера, автоматически исполняющего старые Luau-пакеты.

#### 11. Обязательная проверочная матрица

| Область | Минимальные сценарии |
| --- | --- |
| ABI/package | Core module вместо component; неверный export; неизвестный import; несовместимая версия; повтор ID/command root; path traversal; oversized artifact. |
| Изоляция | Infinite loop в init, callback и cleanup; recursion/stack exhaustion; memory/table growth; множество core memories/instances; trap одного из двух плагинов. |
| Host decoding | Большие длины, nested lists, aliasing строк, неверные tags/encoding; граница квоты и превышение на единицу; host memory не растёт пропорционально неконтролируемому раскрытию данных. |
| Полномочия | Нет grant; чужой storage namespace; поддельный provenance; старый session/entity/plugin generation; privileged direct command. |
| Staging | Команда, затем trap; команда, затем ошибка cleanup; частично корректный batch; переполнение admission. До публикации игровых эффектов нет. |
| Игровые операции | Устаревшая inventory revision; конфликт CAS; одинаковый operation ID с разными данными; повтор после reconnect/restart; item conservation. |
| Доставка | Required outbox full/closed; потеря receiver; результат после commit и отключения гостя; `DurabilityUnknown` не выдаётся за успешный откат. |
| Hooks | Keep/Cancel/Replace; два handlers; stale ticket; duplicate result; queue deadline; отказ обязательной защиты; обход через plugin mutation. |
| Startup | Ошибка configure; одинаковый/изменённый effective plan; отсутствие эффектов `--check`; границы world contract. |
| Reload | Ошибка компиляции/init; превышение памяти кандидатом; незавершённая операция; старые timers/results; сохранение защиты; смена клиентского контракта требует restart. |
| Loader | Vanilla без Loader; несовместимый клиент; отсутствие согласия; UI/audio после disconnect; точная привязка к сессии. |
| Нагрузка | Ноль плагинов; несколько нормальных; один flood/infinite guest; медленный storage; event storm; повторяющийся reload. |

Property-based тесты применять к DTO, размерам, generations и операциям с явными инвариантами. Поведение проверять исполнением, не поиском строк исходного Rust-кода.

Для нагрузочного сравнения сохранить hardware, build profile, seed, число клиентов, сценарий и длительность измерения. Сравнить старый baseline и новый host по tick p50/p95/p99, plugin latency, глубине очередей, CPU/RSS и ошибкам. Debug и release результаты не смешивать. Не уменьшать нагрузку или assertions ради прохождения gate. [R7], [R10]

#### 12. Проверки и порядок работы агента

Использовать существующий harness. Подтверждённые точки входа репозитория: [R10]

```sh
python3 -m tools.harness list
python3 -m tools.harness run correctness
cargo test -p mc-script
cargo test -p mc-test-harness --test plugin_examples
cargo test -p mc-test-harness --test plugin_standard_pack
```

После добавления runtime-крейта:

```sh
cargo test -p mc-plugin-host
```

Внутри этапа выполнять focused tests. На существенном checkpoint — предусмотренные репозиторием gates и независимое read-only review, если среда предоставляет такого агента. Отсутствие отдельного reviewer указывать прямо. Не заявлять, что review было независимым, если выполнена только самопроверка.

Клиентские gates запускать через действующие profiles harness; `--prepare`/`--check` подготовки клиента не являются игровым PASS. Если нужен новый профиль для сборки guest fixtures, добавить его в существующий harness, без отдельного конкурирующего runner.

После этапа обновлять один текущий cursor с: base commit, изменёнными файлами, пройденными проверками, blockers и следующим незавершённым этапом. Доказательства хранить по существующему соглашению `.analysis/validation/` и связанным receipt-путям.

Не создавать отдельный журнал на каждую функцию. Не останавливаться после генерации WIT или успешного `cargo check`, когда критерии этапа требуют реального игрового сценария.

Не выполнять push, merge, release или изменение production deployment без отдельного разрешения. Незакоммиченные чужие изменения, миры и локальные данные сохранять.

#### 13. Что не включать

Не делать marketplace, скачивание исполняемого кода по клиентскому запросу, нативные плагины, второй runtime, автоматический transpiler Luau → Rust, отдельную БД плагинов, новую ECS, универсальную saga, динамический RPC между плагинами, произвольный Java-код на клиенте или общий фреймворк распределённых транзакций.

Не переносить в эту задачу весь resident/settlement game design. Существующие используемые операции сохранить; отдельное упрощение доменной модели требует своей задачи.

Не обещать ускорение только из-за WASM. Цель перехода — проверенный typed ABI, контролируемое выполнение, SDK и единая граница авторитетных операций. Производительность подтверждается сравнительными измерениями.

#### 14. Критерий завершения

Задача завершена после P8, когда реальный внешний Rust-плагин собирается в компонент, подключается без пересборки сервера, работает через существующие игровые владельцы, ограничивается по ресурсам и не обходит permissions. Старые используемые сценарии, startup rules, долговечные операции, reload и Loader перенесены с проверками. Luau production-путь удалён.

Непройденный или недоступный gate остаётся явно незакрытым. Успешный тест нового host не заменяет проверку игрового поведения, сохранений и клиентских сценариев.
